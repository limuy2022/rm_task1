# Point-LIO 稀疏场景失败归因（2026-10-20）

> 历史归因记录：旧实现、补丁和专用工具已从当前仓库移除。下文路径、命令和环境仅记录当时实验，不能用于当前版本。当前实现见[Small Point-LIO迁移验证](SmallPointLIO迁移验证.md)。


本记录针对[视觉定位联合仿真](../教程/Gazebo视觉定位联合仿真.md)发现的往返路径
失败，检查仓库导航压缩包内所带的 ROS 2 / iVox 版本 Point-LIO。所有实验仍在根
Dockerfile 的 `gazebo-sim` 容器内运行，不修改导航压缩包、安装版算法、实车参数值
或运动开关。诊断源码仅复制到容器 `/tmp`，输出放 `build/offline/`。
排查确认了局部平面有效性、处理阻塞导致接收丢样，以及仿真饱和阈值单位遗漏三层问题。
其中仿真参数遗漏已修复；算法和接收队列的变体仍属于临时诊断。

## 1 已确认的局部平面检查缺口

第一项触发链已得到源码、独立几何探针、固定 bag 对照及完整 Gazebo 试验支持：

1. 理想无噪声雷达在静止时重复扫描相同位置，四次快照组成一条 Livox 消息。
2. `laserMapping.cpp` 初始化地图时直接加入未降采样的 `feats_undistort`，重复坐标
   可以进入 iVox。最近5个回波可能只对应两个不同位置。
3. `common_lib.h::esti_plane()` 解线性方程并检查残差，没有检查邻域是否具有足够
   二维空间分布。重复点或共线点可得到低残差，却无法确定唯一平面。
4. 不可靠法向进入位置/姿态更新，形成错误约束；运动之后地图继续吸收受影响的位姿。

这里发现的是**局部匹配邻域退化**。独立审计中，真实表面法向覆盖 x/y/z 三个方向，
理想对应关系的六维位姿信息矩阵最小特征值约0.176、满秩。不能仅凭“两箱体房间”
就断定整间房间没有定位约束。上游的[平面拟合代码](https://github.com/hku-mars/Point-LIO/blob/master/include/common_lib.h)
也采用相同的残差检查逻辑，但本次归因与结果只针对仓库所用版本及本次输入。

## 3 固定16线 input记录的对照

候选平面检查对中心化邻域的散布矩阵求特征值 `λ0≤λ1≤λ2`。`λ2` 过小或
`λ1 < 1e-4·λ2` 时拒绝该邻域，避免把近似直线当成稳定平面。此门槛用于本次
诊断，不是经过实车标定的通用推荐值。

| 变体 | 位置RMSE | 最大位置误差 | 目录 `build/offline/` 下 |
|---|---:|---:|---|
| 镜像安装原版 | 40.81cm | 60.47cm | `lio_replay_original01` |
| 仅加诊断计数，保持原逻辑 | 37.62cm | 60.43cm | `lio_replay_instrumented_original01` |
| 仅初始化地图体素降采样 | 60.04cm | 86.50cm | `lio_replay_init_voxel01` |
| 仅拒绝共线邻域，第1次 | 3.65cm | 10.96cm | `lio_replay_plane_guard01` |
| 仅拒绝共线邻域，第2次 | 6.02cm | 17.16cm | `lio_replay_plane_guard02` |
| 初始化体素降采样+拒绝共线邻域 | 96.85cm | 127.92cm | `lio_replay_both01` |

所有行使用同一bag、相同配置及2倍录制墙钟速度回放，源时间戳不变；各得到401条
定位输出。固定输入没有消除 DDS 与线程调度差异，不应声称逐位确定性。
加入计数会增加计算开销，因此保留了“有诊断但关闭检查”的控制组。

结果支持拒绝无效局部平面是有效方向，也明确否定了“单独初始化降采样就能修好”
的假设。两个改动叠加后仍失败，不能把该组合合并为修复；地图初始化、邻域分布
和后续地图更新仍需更广的测试。

## 5 32线 output的额外排查

原版本次32线output复现位于 `lio_diagnosis_output32_capture01`。它没有每次都复现
之前18.72m的严重发散：本轮定位RMSE9.25cm，但地图外部未知、目标有效率、目标
最大误差与重放后的恢复仍失败。对相同记录进行2倍速回放时，安装原版再次严重
发散，位置RMSE20.16m、仅321条定位输出。

源码还有一个独立线索：`executor.spin_some()` 与整帧处理位于同一循环，雷达与
IMU均使用默认 `SensorDataQoS`。该策略的深度为5、可靠性为best effort，参见
[ROS 2 Humble源码](https://github.com/ros2/rclcpp/blob/humble/rclcpp/include/rclcpp/qos.hpp)。
必须统计估计器回调实际接收量，不能用bag或桥接端的完整样本数证明算法收齐。

进一步发现，早期仿真只将 `acc_norm` 从1换成9.81，却沿用了 `satu_acc=3`。
`h_model_IMU_output()` 使用原始 `acc_avr` 判断饱和，再在测量残差中进行单位换算。
因此静止重力9.81会被阈值3误判为饱和，垂直加速度测量被屏蔽。原3g量程在
m/s²输入中应为29.43。此前32线output的结果不能作为完整IMU约束验收。

以下各行使用同一32线记录、同一个带计数的诊断二进制、相同2倍回放速度：

| 原始饱和阈值 | 平面检查 | 队列深度 | 实收雷达/IMU（记录为404/8083） | 位置RMSE | 最大误差 |
|---:|---|---:|---:|---:|---:|
| 3 | 关闭 | 5 | 363 / 3774 | 52.62m | 169.54m |
| 3 | 关闭 | 8192 | 404 / 8083 | 3.03m | 12.05m |
| 3 | 开启 | 5 | 331 / 3057 | 85.64m | 352.46m |
| 3 | 开启 | 8192 | 404 / 8083 | 6.67m | 24.42m |
| 29.43 | 关闭 | 8192 | 404 / 8083 | 7.88cm | 21.99cm |
| 29.43 | 开启 | 8192 | 404 / 8083 | 7.71cm | 21.57cm |
| 29.43 | 开启 | 5 | 289 / 1570 | 16.80cm | 50.83cm |

目录均在 `build/offline/lio_replay_output32_*`，其中修正单位的目录名包含 `units`。
原阈值、深度5、关闭平面检查时，实际接收的IMU最大时间空洞达0.27秒，尽管
记录的最大间隔只有0.006秒；深度8192则收齐了全部输入。这直接证实接收丢样，
也解释了调度和计算负载为何会改变结果。

诊断工具支持 `--qos-depth`。超大队列会积累延迟，本次只用来区分丢样与其他问题，
不是实时部署建议。回放等待估计输出覆盖记录末尾再评分，`input_drained_to_end`
标记该条件；完整回放精度通过不代表实时吞吐或目标新鲜度通过。

仿真现通过 `team43_gazebo.sensor_config`（现位于 `src/team43_gazebo/team43_gazebo/sensor_config.py`）同时换算 `acc_norm` 与 `satu_acc`，并
在启动前拒绝会把静止重力判为饱和的配置。新增7项回归检查覆盖g与SI的等价
饱和判定、错误SI量程及非法单位尺度。实车配置数值保留原状，只更正误导性的
单位注释；真实量程仍须测量。

最后用正确SI阈值、平面检查及200条接收队列回到完整32线Gazebo场景，输出为
`lio_guard_live_output32_si01`。本轮收到404条雷达、8084条IMU，与记录一致；定位
RMSE5.87cm、最大14.29cm，目标有效时的坐标RMSE6.44cm。但正常窗口目标有效率
仅69.23%，重放后的恢复有效率15.33%，整体仍失败。

`audit_lio_recording.py` 按bag到达顺序，用最近的 `/clock` 减定位原始stamp估算
消费者可用时延：该32线轮次定位到达时延P95为0.530秒、最大0.612秒，约15.46%
超过0.3秒；16线平面检查通过轮次的P95为0.046秒、最大0.080秒，没有超过0.3秒。
这与图像观测只等待0.3秒历史TF、32线目标有效率下降相符。该数是记录端近似值，
尚未逐条还原每个无效状态的全部原因，不能用它精确分摊每种拒绝原因。

这也证实接收完整、最终位置准确与实时可用是三项不同条件；扩大队列没有完成
实时架构修复。仍需处理订阅/计算调度、处理负载和下游定位质量传播。

## 6 复现方法

> **注（2026-10-31）**：本节命令依赖当时独立工作区的 `point_lio` 与三个审计脚本
> （`tools/audit_lio_recording.py`、`prepare_lio_diagnostics.py`、`replay_lio_diagnostics.py`），
> 均已随后端迁移到 vendored `small_point_lio`（`src/team43_lio_backend`）而删除，
> 下述流程不再可直接复跑，仅作为当时排查过程的历史记录。

使用[联合仿真教程](../教程/Gazebo视觉定位联合仿真.md)的同一可选镜像与独立ROS域。
在容器中先source ROS、`/opt/lio_sim/install/setup.bash`，构建并source自己的工作区。
输出目录必须不存在；以下编号供新复现使用。

```bash
# 原版场景预期可能返回失败码1，但仍保存bag、误差和日志。
python3 -B tools/simulate_gazebo_vision.py --scene room --record-bag \
  --output-dir build/offline/lio_reason_capture_01

python3 -B tools/audit_lio_recording.py \
  --source build/offline/lio_reason_capture_01 \
  --output-dir build/offline/lio_reason_audit_01

python3 -B tools/prepare_lio_diagnostics.py \
  --manifest build/offline/lio_reason_build.json
cd /tmp/lio_diagnostics
colcon --log-base /tmp/lio_diag_log build --build-base /tmp/lio_diag_build \
  --install-base /tmp/lio_diag_install --packages-select point_lio --parallel-workers 1 \
  --cmake-args -DCMAKE_BUILD_TYPE=Release
cd /workspace

python3 -B tools/replay_lio_diagnostics.py \
  --source build/offline/lio_reason_capture_01 \
  --executable /tmp/lio_diag_install/point_lio/lib/point_lio/pointlio_mapping \
  --variant original \
  --output-dir build/offline/lio_reason_original_01
python3 -B tools/replay_lio_diagnostics.py \
  --source build/offline/lio_reason_capture_01 \
  --executable /tmp/lio_diag_install/point_lio/lib/point_lio/pointlio_mapping \
  --variant plane_guard --output-dir build/offline/lio_reason_guard_01

# 对早期32线output记录做单位和队列对照；新捕获配置已经自动修正阈值。
# 使用独立新目录，并在 --source 指定实际32线记录目录。
python3 -B tools/replay_lio_diagnostics.py \
  --source build/offline/lio_diagnosis_output32_capture01 \
  --executable /tmp/lio_diag_install/point_lio/lib/point_lio/pointlio_mapping \
  --qos-depth 8192 --set mapping.satu_acc=29.43 \
  --output-dir build/offline/lio_reason_output32_units_01
```

`prepare_lio_diagnostics.py` 逐项校验原源码结构，保留版权/许可证，输出修改前后
SHA256；临时开关为 `RM_LIO_PLANE_RANK_GUARD`、`RM_LIO_INIT_VOXEL`、
`RM_LIO_QOS_DEPTH`，另有平面和输入计数日志。默认不启用算法变体。
`replay_lio_diagnostics.py` 的 `completed` 表示流程完成，`accuracy_passed` 才表示
本段位置RMSE<15cm且最大误差<35cm；不等于地图或目标链的完整验收。

## 7 当前结论的边界

- 已有明确证据支持16线场景的局部平面有效性缺口，候选检查在原失败房间通过。
- 32线output另有饱和阈值单位错误及处理阻塞时的接收丢样，不能统一归咎于平面退化；
  本次对照识别了重要机制，没有对历史每一轮发散做逐帧唯一归因。
- 没有真实MID360输入；理想重复扫描强化了触发条件，不能推断实车发生概率。
- 需要将几何检查、接收/处理能力、定位质量到下游的失效传播分别设计并回归，
  不能只凭本次厘米级误差就宣布正式算法已修复。

本机汇总为 `build/offline/lio_diagnosis_summary/summary.json`，记录14个回放对照及
4个完整仿真；同目录 `comparison.png/pdf` 比较位置误差、32线单位/队列对照和
定位到达时延。诊断源码、二进制及构建日志保存在 `build/offline/lio_diagnosis_bundle/`，
供审阅与复现，不安装到实车。输出均已被gitignore。

另在源码审阅中看到两处 `vector.reserve()` 后直接按下标写入且未找到 `resize()`，
属于需要独立检查的源码风险；本轮没有把它认定为已证实的漂移根因，也没有修改它。

仿真单位修正后的标准容器全量回归：pytest **475通过、1跳过**，C++ **36项无失败**，
离线 **23项作业通过**。日志为 `build/offline/lio_diagnosis_regression.log`。该回归
不替代上述可选Gazebo对照，也不把32线实时链路的失败转为通过。

## 8 云端 CI 回归修复

加入自动仿真后的云端执行再次暴露了该问题。首次运行
[39372202690](https://github.com/limuy2022/rm_task1/actions/runs/39372202690)
雷达位置RMSE 10.19cm，但墙外未知比例仅97.76%，未通过严格地图检查。
后续运行
[39386445669](https://github.com/limuy2022/rm_task1/actions/runs/39386445669)
雷达位置RMSE 56.67cm、最大误差117.83cm、回到起点误差104.94cm，墙体覆盖率
55.37%。同轮常规测试、定位建图及视觉联合任务均通过；雷达任务的原始测量
物理一致性、时间戳顺序及进程退出检查通过。云端没有录bag，不能逐帧归因每次
匹配，但这些结果再次说明单次本地通过不能保证原算法在该理想重复扫描下稳定。

修复将第3节已验证的二维分布检查纳入 `gazebo-sim` 镜像实际安装版，不改变
场景、运动轨迹、地图门槛或算法初始化。对构建副本的 `esti_plane()` 增加
中心化散布矩阵检查和输出有限数检查，采用中心化PCA估计法向和常数项，并保留
原残差门槛。二维判定仍为 `λ2 >= 1e-9` 且 `λ1 >= 1e-4·λ2`，另要求
`λ0 <= 0.01·λ1` 来拒绝跨表面的非平面邻域；没有合并初始化降采样方案。

`apply_point_lio_plane_guard.py` 校验原文件 SHA256 后修改副本，并编译归档中的
实际平面函数进行10项检查：原版错误接受的共线邻域、重复点、近共线、正常平面、
刚体变换、离群点、非有限数、扩展候选后恢复有效平面、过原点平面，以及原版在
原残差门槛内接受的非平面邻域。任意失败会停止镜像构建。原始导航压缩包和
`/opt/lio_sim/src/point_lio` 保留不变，原始函数版权与许可证不变。
仿真 `result.json` 记录 `point_lio_image_build` 清单，包含修改前后哈希与门槛。

仅加入拒绝共线邻域的第一版在云端
[39389272363](https://github.com/limuy2022/rm_task1/actions/runs/39389272363)
仍失败：位置RMSE 8.97cm，但回到起点误差23.28cm；本地亦复现34.14cm的RMSE。
这表明第3节单一固定bag通过不能推广到方形路径。新增带回调计数的完整对照中，
深度5与200分别实收403/8067、403/8066条雷达/IMU，均与各自采集端一致，最大
IMU间隔均6ms，但RMSE仍为27.09和21.49cm；本轮16线失败不能归咎于接收丢样。

在深度5轮次记录的首帧中，对静止原始点做独立KDTree检查：5近邻具二维分布的
比例为0%，10近邻约76.25%。拒绝所有坏平面会让初始阶段缺少雷达约束；因此
进一步将iVox的候选上限从5扩为10，并让平面拟合使用全部返回点，而不是仍只用
前5点。保留至少5个匹配点的要求、邻域二维判据和原残差门槛；不增加仿真噪声，
不扩大iVox查询空间范围，也不改变初始化地图。

只扩展近邻仍不充分：同一方形记录回放中，5点拒绝共线版本RMSE为27.09cm，
10点版本为12.96cm，但完整10点雷达仿真仍有23.61cm的RMSE。进一步改用中心化
PCA的最小特征向量作为法向，通过质心恢复常数项，并增加法向散布检查。
与原 `A·n=-1` 形式相比，这也能正确表示经过原点的平面；残差仍逐点使用原阈值。

最终PCA版本在2核容器、0.25倍率的完整链路中，雷达方形路径位置RMSE为4.48cm，
16项检查全部通过；视觉联合定位RMSE为3.05cm，32项检查全部通过，所有进程正常
退出。日志和报告保存在独立验证检出的 `build/offline/ci_simulation/`。
同一方形记录的2倍速PCA回放曾出现2.90m的RMSE，不作为通过结果；该回放尚无
估计器实收计数，不能据此确定是丢样还是其他机制。当前修复验证范围是CI请求的
0.25倍率、16线input基线，不代表高倍率回放、32线或实车实时链路通过。

本节之后的新镜像默认安装修复版。第6节的原版对照应使用从保留源码构建的
诊断二进制并显式选择 `--variant original`；不指定二进制的回放现在标记为
`installed`，并记录镜像清单，避免误将修复版记为原版。第1～7节均为历史实验，
其中“安装原版”和“仅临时诊断”的描述对应修复前镜像。

修复只纳入仿真镜像；没有修改实车安装、参数值或运动开关。平面检查不能代替
32线接收吞吐、实时延迟或真实MID360验证。

## 9 标准库边界检查与向量尺寸修复

PCA版本的[云端39391890833](https://github.com/limuy2022/rm_task1/actions/runs/39391890833)
四个任务全部通过，但本地重复雷达运行仍出现1.74m的RMSE，同一方形记录的
1倍速回放也出现1.30m，说明不能用第8节的一次完整通过声称所有调度条件稳定。

继续审阅发现，`laserMapping.cpp` 对 `crossmat_list` 与 `pbody_list` 调用
`reserve(feats_down_size)` 后直接使用 `vector[i]`。`reserve()` 只分配容量，
没有创建有效元素，向量尺寸仍为0；下标读写违反标准库约束。修复将两处改为
`resize(feats_down_size)`，保留后续逐元素赋值逻辑。

给原版实际可执行目标启用 `_GLIBCXX_ASSERTIONS` 后，在同一记录的初始化后
处理阶段触发SIGABRT（退出码-6）；没有把未启用检查时的“未崩溃”当作合法访问。
上游CMake会覆盖命令行 `CMAKE_CXX_FLAGS`，因此必须使用
`target_compile_definitions(pointlio_mapping PRIVATE _GLIBCXX_ASSERTIONS)`。
修复头文件增加编译期检查，宏未生效时镜像构建直接失败。源文件、主循环和
CMake均校验原始哈希，报告记录修改后哈希与检查开关。

此处确认了越界行为和原版启用检查后的运行失败，但没有单独证明每一次漂移
都由两处写入引起。平面检查、邻域支持与内存合法性分别保留验证证据；完整链路
继续在启用边界检查的最终二进制上验收。

## 10 新版接收审核与失败查询缓存修复

必须对实际候选二进制重新计数，不能沿用第8节较早的5点版本结果。带计数的
PCA/10点/向量尺寸修复二进制在相同方形bag、2倍录制墙钟速度回放时，深度5
实收403条雷达、7859/8067条IMU（少208条），IMU最大空洞20ms；深度200实收
403/8067条完整输入，最大空洞6ms。中断使这两轮在排空评分阶段报
`ExternalShutdownException`，因此这里只使用已正常退出并落盘的接收计数，
不把未完成的评分当作通过。另一次深度200完整live实收403/8067，仍有1.04m
的RMSE，说明接收完整不能单独保证几何更新正确。

镜像现支持有界的 `sensor_qos_depth` 参数，默认仍为5，仿真副本显式设200。
`input_audit_path` 控制回调端计数文件。仿真在进程退出后读取文件，检查独立采集
端与估计器实际接收量、最大时间间隔及倒序；审核缺失同样失败。保留原有误差、
地图、TF新鲜度和目标恢复门槛，不用增大视觉等待时间掩盖定位积压。

另一个确定源码缺陷是iVox的多近邻查询：无候选时提前返回false，却没有清空复用
的输出容器；调用方忽略返回值，可能再次使用上一帧近邻，并影响后续地图更新。
修复在查询入口清空输出。构建先用实际原头文件复现旧近邻残留，再验证修复后的
成功查询、网格外查询、半径外查询与空地图四类情况。对应独立清单合并进报告。

回放工具还修复了排空误判：定位的最后可用点为40.276秒，而真值末帧为40.33秒，
旧的“真值末尾减50ms”要求会错误报告未排空。现在按末条Livox消息中实际可被
归档AVIA预处理接受的点确定目标，容差1ms，并检查尾部IMU支撑；少完整末帧
仍失败。播放超时按录制墙钟时长除以倍率再加30秒推导（至少180秒），报告同时
记录预期末点、实际末点及播放时长。排空完成与定位精度、接收完整分别判定。

## 11 测量方差的分支一致性修复

更深的滤波器审阅确认，`esekfom.hpp::update_iterated_dyn_share_modified()` 的
两个等价计算分支对同一个测量噪声标量含义相反。少量观测分支计算
`S = H P Hᵀ + R I`，把它当方差；大量观测分支却计算
`P⁻¹ + R HᵀH` 并在增益末尾乘R，把它当逆方差。当前R为0.01，两种解释的
观测信息权重相差10000倍。input状态维度为24，有效观测行数跨越24时切换分支。
点按体素平均时间分组、再经平面有效性筛选，因此组内有效行数可随输入细节改变。

修复仅把大量观测分支的两处乘R改为除R，使之为
`P_post = (P⁻¹ + HᵀH/R)⁻¹`、`K = P_post Hᵀ/R`，不更改测量方差配置。
构建时直接实例化实际上游滤波模板，以24维线性状态比较23个有效观测、补零到
24行、以及重复到46行并把方差加倍这三种等信息输入，覆盖R=0.01、1、100。

原版R=0.01时，23行增益0.999565406345，补零一行后变为0.186991869919；
修复后均为0.999565406345。三档方差的状态及协方差一致，最大协方差差约
7.9e-15。原版不一致及修复后9种构造均在镜像构建期验证；清单记录实际模板
哈希并合并进仿真报告。该数学缺陷独立于输入丢样、向量尺寸与近邻缓存问题；
完整场景仍需以修复后的实际运行指标验收。

## 13 接收连续性审核须参照真实源序列

上述镜像的[云端39433479508](https://github.com/limuy2022/rm_task1/actions/runs/39433479508)
常规测试、导航和雷达通过；视觉定位RMSE为0.010775m，目标位置RMSE为
0.020934m，原32项全部通过，但新增雷达连续性审核误报失败。

原因是审核将名义10Hz写成严格100ms，而云端软件渲染及桥接形成的真实采样
并非完全等间隔。此轮403/403帧全部收到且无倒序，估计器最大间隔126ms；
输出末点时间也有124ms与126ms两处间隔，批内快照跨度最大100ms。
IMU独立采集CSV中35.726→35.736秒的10ms间隔，同样出现在接收审核中。
不能把源端已有的采样空洞归因于估计器订阅丢帧。

现于每条Livox实际发布处记录原始header时间，持久化完整时间戳序列；对照
估计器实收最大间隔是否超过源序列最大间隔加1μs。IMU使用独立采集端真实
时间戳作同样比较，并单列源IMU的10ms质量限制。数量和顺序检查、原有
批内跨度、物理输入、地图、定位、TF新鲜度及故障恢复门槛均保留。

14项容器pytest覆盖126ms真实源抖动通过、接收丢样/新增空洞/倒序失败、
源IMU质量不合格失败、源序列异常及审核缺失失败，并验证审核不能覆盖已有失败。
因此不是将100ms常量随意扩大到126ms或150ms，而是分别审核源采样质量与
传输到估计器后的新增缺口。当前报告在原21/37项基础上增加一项源IMU检查。

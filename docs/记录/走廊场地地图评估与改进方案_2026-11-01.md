# 两门之间走廊：地图评估与改进方案

本次依据：`data/` 中两张上午地图、截断的原始录制压缩包，以及用户确认的“比赛场地是两扇门之间的长方形走廊”。本文件给出改进方案，不代表已完成新的实物定位验收；尚未切换比赛默认地图或修改定位算法。


实施进展：用户进一步确认地图不评分、无需地图避障，并授权简化。现已按此实现默认corridor模式与不依赖地图的direct建议速度；操作以[比赛启动与收尾](../教程/比赛启动与收尾.md)为准。下文保留数据检查及当时完整旧图方案的分析，不再要求比赛前完成旧图纵向重定位。原始数据已确认无法取回，不将重新传输作为比赛前置。
后续确认：两扇门的开关状态可能变化，用户目前不能在地图中可靠指出它们。因此不以手工标门为启动前置，不自动裁出所谓赛区，也不根据猜测擦除门扇。先保留完整原图，依靠当前点云、固定墙体与可辨认的门框验证位置。

## 3 最高优先级：确定赛区覆盖，选主图与备份图

1. 在两张预览中确认两扇边界门及其间走廊，对照墙面突出物、门框与现场照片，不以图像上下直接代表真实前后。
2. 检查两门之间的两侧墙、可行驶区域、端部特征是否都已观测。门外未知区可以保留为未知，不补成白色。
3. 若第一张完整覆盖门间区域且墙体无明显重影，可先列为主图候选；若第二张墙体更一致或覆盖更合适，则以第二张为候选。面积不是最终选择依据。
4. 在下午允许准备的时间，分别用当前真实点云验证候选图：底盘放在已扫到的门框附近，给 RViz 初始位置与车头朝向提示，检查叠图及沿走廊方向是否错位。
5. 选通过验证的一张作为比赛图，另一张单独保留为备份。每次更换图都在开赛前重启并重新定位，不能在本轮对齐已固定后热换地图。

不直接将两张图拼接，也不把走廊手工画成理想矩形。不同会话需先估计相对位姿；未观测区域、活动门扇及墙体漂移不能靠图像覆盖解决。

## 4 最高优先级：针对长走廊调整重定位操作

当前 `saved_map_node` 在开赛前进行一次二维匹配，连续三个候选稳定后固定变换；之后依靠下午新会话 LIO 跟踪运动，不会持续用上午地图修正定位。

长走廊里，如果点云主要是两侧平行墙，横向位置与朝向比较容易受约束，沿走廊方向可能有多个相似解。连续三次稳定只说明结果稳定，不能单独证明位置正确。当前匹配点范围小于 8m，站在走廊中间也未必能看到两端门框。

现场优先采用：

1. 在规则允许的位置，选靠近其中一个门框或其他固定、非对称结构的位置初始化；不必回到上午起点。
2. RViz Fixed Frame 设 `survey_world`，显示 `/team43/survey_map`。
3. 用 `2D Pose Estimate` 提示底盘中心和车头朝向；现有实现搜索提示附近 ±1m、±30°，提示也需要足够接近实物。
4. 等 `/team43/relocalization/status` 中 `aligned=true`，显示当前 `/red_standard_robot1/cloud_registered`，检查两侧墙与门框同时重合，尤其检查沿走廊方向的错位及反向匹配。
5. 若不对，在裁判开赛前重启并修正提示；当前对齐固定后不再接收新的初始位置。

门框、墙角属于较稳定参照；活动门扇可能改变，应确认上午和下午开关状态。只有某扇门上午和下午结构对应且可见时，才可将其当作匹配依据。不能把“门关着”视为永久占用事实，也不能在地图里直接删除尚未确认的黑块。

现已确认门状态可能变化，因此优先使用固定部分同时匹配，不能只检查一块疑似门扇是否重合。若门扇差异导致候选失配，先换到固定特征更多的位置或改善提示；如需代码适配，再实现对局部变化的鲁棒匹配并验证其不会接受纵向错误位置。当前均值截断具有一定容错，但没有专门的门扇识别功能，不能宣称已解决。

另外，定位和建议速度是两件事：旧图中关门形成的占用可能在下午开门后仍挡住建议方向；反过来，旧图开门也不表示下午仍能通过。需要改进时应单独增加实时障碍证据用于建议速度，不直接擦改提交用的原始地图，也不以“匹配成功”证明通道畅通。本程序给建议速度，底盘仍由主办方控制。

不建议为了启动而取消多解判断、降低匹配门槛或强行将提示当作精确定位。应先改善起始位置的几何特征与提示质量。

## 5 取得完整原始数据后，优先重建什么

按《原始数据录制与离线建图》的独立 Docker 回放流程，重新运行 LIO 和栅格建图，保留原图作为基线。

- 若确认门间赛区触及边界：保持 0.05m 分辨率，扩大窗口或平移 origin 覆盖两门间区域，并留余量。例如 40×40m、origin [-20,-20] 只是候选，必须按回放轨迹验证是否足够；不要盲目更改为低分辨率。
- 仅扩大 PGM 画布不能恢复原先丢弃的点；需要重新回放原始数据累计地图。
- 对两侧墙是否平行、是否有重影进行对照。墙体随行驶逐渐弯折或重复，优先排查 LIO 轨迹、时间与退化，不靠擦图拉直。
- 如果门外区域较多，可在明确两门位置后派生赛区视图；用于定位的地图可保留附近真实固定结构。裁剪后的 YAML 原点必须同步计算，原始快照仍完整保存。
- 调整障碍高度仅在证据表明地面误入或关键固定结构被漏掉时进行，不把障碍阈值当作墙体重影修复手段。

## 6 如需进一步改代码，按收益排序

**第一项：地图选取与状态提示。** 增加明确的地图文件选择和摘要，显示赛区边界是否接触图边、匹配用图名、候选分数、备选解、当前是否仅依靠里程计。避免选错图与误解“重定位完成”。

**第二项：走廊退化检测与匹配验证。** 检查沿走廊方向移动候选时评分是否接近；对相近分数的位移带保留“不唯一”状态。可扩展为短时间内多帧点云一致性验证，但两面无限平行墙本身不提供纵向定位信息，多帧也不能凭空制造唯一位置。需门框、端墙或可信位置提示。

**第三项：连续地图定位。** 现有实现只做初始跨会话对齐。若实测长距离运动后明显漂移，可增加独立于比赛坐标原点的连续 scan-to-map 定位模块；需限制跳变、处理门扇变化、多解与失配，并回归目标坐标和 CSV 链。它不是简单打开一个现成参数，不建议比赛前未经回放与仿真验证就替换主链。

实施验证顺序：新旧地图读取与 origin 测试 → 对称走廊及门框合成回归 → 原始数据 Docker 回放 → 分时启动和评分回归 → 现场真实叠图。当前数据检查未运行新的 ROS/Gazebo 验收，不把方案写成已验证结果。

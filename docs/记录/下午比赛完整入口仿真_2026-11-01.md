# 下午比赛完整入口仿真（2026-11-01）

本次针对当前唯一下午入口进行演练：项目maps地图直接复制交付，正式比赛位置由LIO和replay_start确定，不等待旧图重定位。全部在根Dockerfile的gazebo-sim环境运行，挂载/workspace，构建和安装均放/tmp；没有访问真实雷达、串口，也没有向正式/judge话题发布消息。

## 实际走过的程序

`tools/start_match.bash` → 真实`match.launch.py` → Point-LIO、ArUco检测/PnP、底盘中心换算、世界对齐、目标估计、实时点云保护、评分写盘和C++串口桥。先用默认ID=-1启动，再执行真实`tools/set_target.bash 0`；保留motion_enabled=true、continuous=true的比赛默认值。

硬件Livox进程替换为不连接SDK的空节点；串口连接新建PTY，输入固定云台反馈，检查实际C++桥的命令及零速帧。评分消息重映射至隔离域`/test/match/*`，评分源与CSV读盘观察器分别运行在独立进程。

## 两种输入，不混淆测试范围

移动演练先用唯一的`corridor.sdf`场景生成三维雷达、IMU和真实Gazebo渲染图像，并保留rosbag及真值。仅增加固定相机和ID0、黑框7.5cm的实体码，不增加其他场景。

随后用`tools/afternoon_gazebo_inputs.py replay`按原始传感器时间1倍速发送；点云等帧内最后一个真实点完成采样后才发送，其余消息按header采样时刻发送；所有header和点云内绝对纳秒时间统一平移到当前墙钟，扫描内时间差、IMU单位和运动速度均不缩放。这样生产入口仍用墙钟，10Hz评分与写盘时限可按真实墙钟检查；不是把慢速Gazebo的时间冒充实时截止。

该仿真平台为平装，底盘中心取平台IMU原点，故显式传入仿真外参、SI加速度单位和地面高度；相机安装链与比赛配置一致。不会改动实车vehicle_field.yaml或调小定位滤波器体素参数。Gazebo真值只供离线比较，未送入生产定位/估计节点。

15分钟长测使用原有合成静止传感器，通过相同实际脚本、生产节点、串口桥及独立评分/观察器发送9000拍。它验证完整运行时长和逐拍提交，移动精度由前述Gazebo演练单独验收。

## 当前已完成结果

- 全量构建16包；Python 661项、C++ 49项、离线编排20项通过。
- Gazebo移动演练250拍：250行九列有限数字，逐行时间严格等于原tick stamp，保留6位小数；最大可见延迟18.77ms，P99为2.54ms，0行超过60ms。测试观察器60ms门槛比题目100ms要求更严格，未放宽。
- 比赛坐标下底盘最大误差0.98cm、RMSE 0.28cm；固定目标最大误差3.96cm、RMSE 1.70cm；100ms预测最大误差4.74cm。运动轨迹包围盒对角跨度0.757m，包含纵向和横向往返。
- 第0拍有1行降级零目标：该拍起点/TF还未就绪，但按时写出；未把它当成正确目标坐标。精度统计在开赛1秒后进行，逐拍行数和截止统计包含全部250行。
- 确认指定目标后自动跟踪；相机断流停止、恢复、参数解除使能停止、运动时Ctrl+C发出三帧零速、所有比赛进程正常退出，均通过。
- 地图只复制、不产生运行栅格消息；PGM内容和YAML参数未被评分过程中改写。
- 真实record.bash录制并校验SQLite/metadata后，在新ROS域、新LIO进程中重放：55条定位、5幅地图，323个占用格、4786个空闲格，保存和三个进程退出均正常。

- 评分中断流演练（另250拍）：第100..119拍停发图像，评分中确实丢弃30帧真实原始图像（收尾停转测试另丢12帧）；250行均写出，最大可见延迟2.95ms。丢失时目标降级且建议归零，恢复后目标自动恢复；底盘最大误差0.87cm，目标最大误差3.32cm，精度窗口明确排除故障与恢复期，截止统计不排除任何行。退出后地图内容仍保持不变。
- 独立近墙Gazebo场景：12项判据全部通过，2449条建议、2252条有效建议，所有有效前瞻路径的真实最小墙间距0.40155m；侧墙改变建议方向、端墙限速、点云断流90个样本均归零、恢复后重新建议。底盘定位最大误差2.01cm。

- 最终版回放调度另外确认：点云只在帧内最后一点采样完成后发布，避免提前发送未来扫描数据。`moving_final`再跑250拍并注入相机中断：全部通过，最大写盘可见延迟4.78ms；底盘最大误差1.53cm、RMSE 0.37cm，目标最大误差4.56cm、RMSE 1.76cm，预测最大误差6.02cm。故障期与起点初始化（第0、1拍）导致共19行零目标，均保留在输出和时限统计中。

首次15分钟长测`full_15min`：9000行全部按时写出，最大可见延迟27.15ms、P99 2.85ms、0行超过60ms，但整链验收失败，不能标成通过。约第30秒底盘更新出现约200ms缺口、关节解算约300ms没有更新，触发原有200ms关节反馈锁停保护，之后未人工重新使能；9000行内另有34行零目标。该轮同时运行Gazebo和其他测试，输入发布与观察又共用一个Python循环，已有证据不能把缺口完全归因某一进程，故保留为高负载/输入中断失败证据。

随后将合成雷达、雷达IMU、图像和虚拟MCU输入拆为独立进程，记录实际发送间隔，避免观察器回调或命令等待影响硬件输入；不修改生产200ms保护、不自动清除锁停、不放宽评分截止。100拍检查通过后，独立重跑9000拍。新增验收判据：评分期间出现任何锁存反馈故障，整轮失败，不能只看CSV行数。

最终`full_15min_independent`完成：9000拍、9000行，九列有限数、逐拍stamp与六位小数全部匹配；最大可见延迟21.53ms、P99约2.75ms，0行超过60ms，且整轮没有任何锁存反馈故障。相机丢失停止/恢复、参数解除使能、运动时Ctrl+C三帧零速、全进程退出码0、退出后地图PGM字节和YAML参数保持不变，全部通过。输入源发送9022帧点云、162660条雷达IMU、44062帧虚拟MCU反馈；最大间隔分别102.62ms、10.03ms、25.60ms。

**持续目标有效性仍有未解决项**：共45行目标为零，其中第0拍1行、开赛1秒后44行；运行中占约0.49%，与短时图像新鲜度告警相伴，之后恢复，没有引起程序退出或反馈锁停。不能把这些行当成准确坐标或称“每拍都跟踪正常”。非零目标行最大误差0.52cm只说明该静止合成输入下的有效样本，不能掩盖上述降级行；NUC持续相机接收与处理负载还需现场验证。当前报告的通过范围是软件链路、逐拍按时输出、已列故障恢复与停止行为。

操作指南已补充检查状态与数据恢复后重新使能的方法；不能以CSV仍增长当作跟踪持续有效。

## 复现（仅隔离容器）

先按测试运行指南构建并source `/tmp/ci/setup.bash`，不要在公共NUC执行这些评分注入工具。每次output目录必须是新目录。

```bash
export ROS_LOCALHOST_ONLY=1
ROS_DOMAIN_ID=98 IGN_PARTITION=team43_afternoon \
  python3 -B tools/afternoon_gazebo_inputs.py capture \
  --record-dir build/offline/afternoon_demo/gazebo_capture

python3 -B tools/verify_match_workflow.py --count 250 \
  --gazebo-record build/offline/afternoon_demo/gazebo_capture \
  --output-dir build/offline/afternoon_demo/moving_match

python3 -B tools/verify_match_workflow.py --count 250 --inject-camera-fault \
  --gazebo-record build/offline/afternoon_demo/gazebo_capture \
  --output-dir build/offline/afternoon_demo/moving_faults

python3 -B tools/verify_match_workflow.py --count 9000 --ros-domain-id 87 \
  --output-dir build/offline/afternoon_demo/full_15min
```

实际证据根目录为`build/offline/afternoon_20261101/`，没有提交到git。每次演练保存result.json、真实启动日志、set_target日志、反馈时序、正式输出副本和配置快照。`gazebo_capture/sensor_bag`保存原始数据，`truth.csv`只作比较；`source_manifest.json`记录时间平移及发送统计。

首次`moving_match`因测试回放源使用best-effort而生产图像/仿真IMU接收端要求可靠QoS，未收到图像而失败；日志保留。修正回放源为可靠发布后，`moving_match_qos_fixed`完成上述通过结果；没有修改生产订阅要求或放宽时限。

首次`moving_faults`发现相机故障注入回调的开关被Probe.pump的局部状态恢复覆盖，实际图像未中断，故“断流时应降级”判据失败。修复测试夹具的独立断流状态，并新增原始源丢帧时间戳核验后，`moving_faults_injection_fixed`通过；没有把未注入的故障伪报为生产程序通过。

## 现场仍需确认

这些结果验证软件连接、仿真输入的坐标链及本机容器中的提交时限。固定反馈的PTY不能证明真实电机闭环；仿真没有MID360扫描模式、真实安装误差、轮胎动力学或现场噪声。正式NUC仍需确认驱动/串口权限、现场雷达网络、相机内参和实际负载；不能用本报告保证实机精度或100%无故障。

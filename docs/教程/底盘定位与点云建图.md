# 用已有 Point-LIO 定位，再把点云变成二维地图

B 输入命令，C 在 RViz 观察点云、点击地面、检查墙和通道，A 核对 frame 与最终装车配置。以下不控制轮子、不启动第二份雷达驱动；主办方负责驾驶底盘。跟踪试转不必等建图。

## 1 先保留 NUC 原来能找到 Point-LIO 的环境

B 在 **NUC 原本用于 ROS 调试的终端**中，先不要执行跟踪包的 `use_here.bash`，输入：

```bash
ros2 pkg prefix point_lio
```

应打印一个已安装包的目录。把这行路径记下：它说明当前终端已经找到 Point-LIO。然后在**同一终端**叠加本次跟踪包的安装目录：

```bash
TRACK_WS="$HOME/ws_championship/src/47-visual-tracking-20261018-r3"
source "$TRACK_WS/install/local_setup.bash"
ros2 pkg prefix point_lio
ros2 pkg prefix gimbal_tracker_bringup
```

`TRACK_WS` 沿用[云台跟踪教程](云台跟踪.md)中已经设置的本次工作目录。第一条包路径应仍为刚才记下的 Point-LIO 路径；第二条应指向本次 `$TRACK_WS/install` 内的 bringup 包。这里特意用 `local_setup.bash` 保留原来的定位环境；**不要在这一步换用会清空环境的 `use_here.bash`。**

如果第一次就显示 `Package not found`，说明当前终端没加载 Point-LIO 所在的工作区，或它尚未安装。保留这条输出，请现场负责人指出选手可用的安装工作区；在本终端加载其 `install/setup.bash` 后重试。不读取保护目录，不安装依赖，不尝试整工作区重编译。这不影响继续测试已经交付的图像跟踪程序。

## 2 看清输入，再只启动定位

B 输入：

```bash
ros2 topic type /livox/lidar
ros2 topic echo /livox/imu --once --qos-reliability best_effort
```

第一条应显示 `livox_ros_driver2/msg/CustomMsg`，这是这份 Point-LIO 当前配置要求的格式。如果显示 `sensor_msgs/msg/PointCloud2`，保留结果，不把它当作同一种输入硬接。若实际使用的是 `/red_standard_robot1/livox/lidar` 与 `/red_standard_robot1/livox/imu`，下文两条输入参数都换成对应完整名字；不再启动第二份雷达驱动。

第二条应输出一条有时间戳、有限加速度与角速度的 IMU 消息。雷达静止时，用 `linear_acceleration` 的 x、y、z 计算 `sqrt(x²+y²+z²)`：当前 `point_lio_mid360.yaml` 的 `mapping.acc_norm=1.0` 对应 g 单位，结果应接近 1；若接近 9.8，则应在自己的参数副本中把 `mapping.acc_norm` 改成 `9.81` 再用 `params_file:=...` 指定。**看三个分量的模，不要求雷达水平，也不把云台 IMU 的结果当作雷达 IMU 单位。**驱动与雷达数据说明见[官方 MID360 教程](https://blog.secaumene.com/kit/mid360-lidar.html)。

输入符合这份配置后，B 启动：

```bash
ros2 launch gimbal_tracker_bringup lio_only.launch.py \
  lidar_topic:=/livox/lidar imu_topic:=/livox/imu
```

此终端保持运行。用保留同一 ROS 环境的另一个终端输入：

```bash
ros2 topic echo /red_standard_robot1/aft_mapped_to_init --once
```

应看到 `header.frame_id: camera_init`、`child_frame_id: body`，以及有限的位置和有效四元数。这里的 `body` 是 Point-LIO 估计的 IMU 坐标，**还不是底盘中心**。本版本也没有填充输出消息的 `twist`，不能据此说速度为零；现有底盘转换器已准备按位姿与源时间戳求速度，不需重写订阅节点。

C 保持雷达静止，B 观察位置是否仍在持续刷新、是否明显跳变；移动雷达或底盘的实际动作留到现场按已有装配条件执行，不触碰正在转动的机构。若一直收不到位姿，先保留 Point-LIO 终端的第一条报错以及上面两条输入结果；不要为了找输出再起完整 Nav2。退出本次定位只在其终端按 Ctrl+C。


## 3 观察真实点云，再启动地图节点

RViz 的 Fixed Frame 选 camera_init，添加 PointCloud2，话题选 /red_standard_robot1/cloud_registered、Reliability 选 Best Effort。应看到墙面、桌椅等结构；静止时不应持续明显漂移。camera_init 是 Point-LIO 的里程计 frame 名，不是相机 C。参考[主办方导航实操的定位和可视化步骤](https://blog.secaumene.com/nav-intro/practice.html)。

B 在一个新终端输入：

```bash
source "$HOME/ws_championship/src/47-visual-tracking-20261018-r3/use_here.bash"
ros2 topic echo /red_standard_robot1/aft_mapped_to_init --once
```

应有 `frame_id: camera_init`、`child_frame_id: body` 和有效位姿。这个 `body` 是LIO的IMU坐标，不是底盘中心。再执行：

```bash
ros2 launch gimbal_tracker_bringup cloud_mapping.launch.py output_dir:="$TRACK_WS/maps_camera_init"
```

这条只起建图节点，不驱动硬件，不发布TF，不启动电机。它读取同一份 `point_lio_mid360.yaml` 的雷达相对IMU偏移，结合完整位姿确定射线起点；输入点云已经在世界系，**不再乘一次位姿**。若现有Point-LIO使用了自定义参数文件，这条命令也增加 `lio_params_file:=同一文件完整路径`，不要让两边使用不同固定外参。

另一个新终端同样 source R3 后：

```bash
ros2 topic echo /team47/cloud_mapping/status
```

正常有点云时应显示 `需要确认地面高度`、`frame_id: camera_init`、z分位数和光心位置。若显示“等待完整body位姿”，核对两条话题来自同一个LIO实例、时间戳在同一时钟，保留状态和LIO终端错误；不要只把frame改成想要的名字。

## 4 C 在 RViz 点地面 B 录入读到的高度

1. RViz 的 Fixed Frame 选 `camera_init`，添加 PointCloud2，话题 `/red_standard_robot1/cloud_registered`，Reliability选Best Effort。
2. B另开终端并source本包，输入：

```bash
ros2 topic echo /clicked_point
```

3. C在RViz工具栏选 **Publish Point**，在清楚可见的地面点云上点三处。不要点墙、桌面或墙脚。B记录三条消息的 `point.z`。
4. 三个值应接近，取中间值作为地面z。**这是camera_init坐标中的地面高度，不是拿尺子量的雷达离地距离。**若三处差得很大，先检查是否真的点在同一平面，不直接确认。
5. 假设实际读数为 `-0.78,-0.80,-0.79`，中间值为 `-0.79`。以下数字仅示例，必须替换为现场值：

```bash
ros2 param set /team47/cloud_mapping_node floor_z -0.79
ros2 param set /team47/cloud_mapping_node floor_confirmed true
```

下一帧开始，应显示“正在建图”，`accepted_scans`、`n_free`、`n_occupied`逐渐增长。这里只确认地面，不要求重做相机标定、O/C、完整底盘外参。

## 5 看图 保存和判断对不对

RViz添加Map，话题选 `/team47/slam_map`。应看到障碍轮廓、观察到的空闲区，以及仍为未知的区域。墙不应因雷达/底盘转向而出现另一套平行轮廓；未扫描到的地方不应凭空全变空闲。地图不自动膨胀，原始障碍和自由区保留给后续建议方向使用。

保存：

```bash
ros2 service call /team47/save_slam_map std_srvs/srv/Trigger "{}"
ls "$TRACK_WS/maps_camera_init/47_slam_map.pgm" "$TRACK_WS/maps_camera_init/47_slam_map.yaml"
```

应返回 `success: true` 并列出两个文件。默认也每10秒保存有更新的地图；Ctrl+C退出时保存最后有效地图。若没有确认过的有效地图，保存请求明确失败，不写一张看似正常的空地图。

这是 `camera_init` 中的源地图，**不是最终比赛起点地图**。正式链由现有 `grid_mapper` 结合真实 `map←camera_init` 转换，再输出 `47_map.pgm/yaml`；不能只改文件名或frame标签。

初始窗口20×20m、分辨率5cm，原点[-10,-10]；实际场地更大时复制并编辑 `cloud_mapping.yaml`，启动增加 `params_file:=你的副本`。光心移出地图会报错，不循环覆盖到另一边。

默认障碍高度是地面上方0.15～1.8m，地面容差±0.08m。**这些是初始配置，不是官方规定；0.15m会漏更低的不可跨越台阶。**现场看到低障碍时，在自己的配置副本调整 `obstacle_min` 和 `ground_tolerance`，停掉建图后重新开始，别把两套地面高度混进同一张图。当前算法面向重力对齐的近似平地，不宣称已解决坡道/楼梯和长期动态建图。

本机另测20k/50k点更新约41～64ms，不含ROS；`publish_hz=1`只控制地图发布频率，不限制点云处理频率。NUC上若积压、丢帧或拖慢跟踪，保留状态和CPU现象再针对性节流。


## 6 地面与配置的两个易错点

只有还没有接受有效扫描时才能改 floor_z/floor_confirmed。输入错了、已经开始建图，就 Ctrl+C 停掉建图进程，换新输出目录重启；别把两个地面高度混成一张图。地图尺寸、障碍高度、ground_tolerance 等启动时读取，改自己的参数文件后同样要重启。

launch 的 floor_z / floor_confirmed 默认值会覆盖 YAML，所以只在 YAML 写 true 不会启用。第一次用第 4 节的 ros2 param set；后面已知地面值时可在启动命令显式加 `floor_z:=-0.79 floor_confirmed:=true`，数字用实测值。

此节点只生成源地图；有点云不等于底盘定位准确。后续由主办方驾驶时，记静止 30 秒漂移、已知距离直行、转弯和返回标记点的误差。先确认参考点是 body/IMU，再利用实测安装尺寸换到底盘中心，具体见[坐标与整车接入](坐标外参与整车接入.md)。

# 定位与建图的 ROS 2 集成仿真

本页是轻量的定位输出接入验证。需要实际运行 Point-LIO 时，使用[Gazebo 原始雷达与 IMU 仿真](Gazebo雷达惯性定位仿真.md)。

这项试验检查：给定已知的 Point-LIO 格式输出，四个真实节点能否把点云变成
正确地图、把 IMU 位姿换到底盘中心、按起点消息的时间冻结比赛坐标，并导出
一致的 PGM/YAML。它不运行 Point-LIO，不据此宣称实机定位精度或评分链通过。

## 1 使用什么工具

| 工具 | 在这项试验里的作用 |
|---|---|
| 根 `Dockerfile` 的 ROS 2 Humble 镜像 | 与仓库测试使用同一环境；不在宿主安装 ROS，不用 pip 改系统库 |
| Python + NumPy | 在尺寸已知的房间中做射线求交，生成已配准点云和带真值的合成 IMU 位姿 |
| rclpy + DDS | 跨进程传输真实 `PointCloud2`、`Odometry`、`OccupancyGrid` 和服务调用 |
| ROS `/clock` + `use_sim_time` | 统一输入时间、节点定时器和 TF 时间；不测 NUC 实时吞吐 |
| Pillow | 将真实导出的地图与真值墙面、底盘轨迹叠加为 PNG；无桌面也能检查 |

本轮不依赖 Gazebo。场景是带高度的平面射线模型，不模拟轮胎动力学、MID360
非重复扫描、逐点时间、运动畸变、雷达遮挡材质或 IMU 积分。已知位姿相当于替代
Point-LIO 的输出，因此目前验证的是定位输出之后的接入链。

四个生产可执行程序各自在独立进程中运行，不通过直接调用回调代替通信：

```text
Python 场景真值
  ├─ 合成 body 位姿 → base_pose_provider_node → map_frame_broadcaster_node
  └─ 合成 camera_init 点云 → cloud_mapping_node → grid_mapper_node
                                                   ↑
                                        比赛起点与静态 TF
```

试验节点通过公开参数服务启用仿真时钟，保留生产节点工厂的系统时钟默认策略。
所有数据话题、TF 和模拟开赛信号都在 `/sim/navigation/*`；只有 `/clock` 使用
标准名字。必须使用独立容器、`ROS_LOCALHOST_ONLY=1` 和独立 ROS 域。
不启动传感器、串口或电机，不向 `/judge/*` 发布任何消息。

## 2 如何运行

在仓库根目录先构建现有测试镜像：

```bash
docker build -t rm-task1-humble-test .
```

一次执行两个场景：无噪声房间、标准差 1cm 的独立高斯测距噪声。
输出目录必须尚不存在；再次运行换新编号，保留对比产物。

```bash
docker run --rm -v "$PWD":/workspace -w /workspace \
  --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -e ROS_DOMAIN_ID=87 -e ROS_LOCALHOST_ONLY=1 \
  rm-task1-humble-test bash -c '
    source /opt/ros/humble/setup.bash &&
    colcon --log-base /tmp/clog build --build-base /tmp/cb \
           --install-base /tmp/ci --symlink-install &&
    source /tmp/ci/setup.bash &&
    python3 -B tools/simulate_navigation.py \
      --output-dir build/offline/navigation_sim_01'
```

在已经构建、source 的同一交互容器内，可只跑一项：

```bash
python3 -B tools/simulate_navigation.py --scenario clean \
  --output-dir build/offline/navigation_sim_clean_01
```

固定随机种子默认为 47；`--seed` 可换种子，`--scans` 默认为 160，至少 120。
种子控制测距噪声，不保证不同主机的 DDS 到达顺序与订阅条数完全相同。
脚本退出时停止自己启动的四个进程，不影响其他 ROS 进程。

## 3 场景和验收

房间边界为 x=[-3,4]m、y=[-2,3]m。底盘从非零位置、yaw=0.7rad 开始，
先静止后绕一圈，途中有小幅 roll/pitch。body 相对底盘的平移和旋转都非零；
雷达相对 body 的平移从现有 `point_lio_mid360.yaml` 读取。这里的底盘安装值
完全是仿真值，不能复制为实车外参。

前段出现临时行人，后段从多个方向重新扫描其原位置。点云与位姿交替先到，
开赛信号也故意延迟送达，检查待匹配队列和按历史时间冻结起点的行为。

| 检查 | 本试验门槛及含义 |
|---|---|
| 墙体覆盖 | 真值墙面一格邻域内有障碍的比例 >97% |
| 室内空闲 | 离墙至少约 20cm 的采样点中，空闲比例 >97% |
| 墙外未知 | 离墙超过 15cm 的外部采样点必须全部保持未知 |
| 墙厚/杂散占用 | 占用格中心到最近真值墙面的距离 P95 <8cm |
| 临时行人 | 原位置内部采样点不再有占用残影 |
| 底盘中心、比赛起点、姿态、速度转换 | 与解析真值误差 <1e-6；这是确定性坐标运算门槛，不是定位精度指标 |
| 订阅覆盖 | 比赛坐标位姿条数至少为输入扫描数的 85% |
| 地图导出 | 真实地图消息与源 PGM 像素一致；比赛图保留格子，正确转换 origin 的 x/y/yaw |
| 输入保护 | 地面未确认不建图；无有效地图时保存失败；错 frame、过期、未来、重复时间戳不污染地图 |
| 匹配和恢复 | 错位姿/缺同时间位姿不污染地图；停止输入报告过期；合法输入恢复后继续更新 |

这些是当前合成场景的工程回归门槛，不是官方评分标准。地图看起来正常也不能
跳过 `result.json`；任何失败都会以非零状态退出，日志和产物保留以便排查。

验证验收器能发现错误时，可做一个故意失败的对照：

```bash
python3 -B tools/simulate_navigation.py --scenario clean --inject-mount-error \
  --output-dir build/offline/navigation_sim_wrong_mount_01
```

它仅把待测底盘转换器的安装 x 偏移加错 25cm，场景真值保持不变。
应退出非零，`base_mount_conversion` 等检查应失败。如果这轮也通过，先检查
验收器本身，不把它作为正确结果。

## 4 查看产物

根目录 `result.json` 汇总场景结果，并显式记录 `Point_LIO_executed: false`。
每个 `clean/`、`range_noise/` 子目录含：

- `overview.png`：真实导出源地图；蓝线为真值墙面，绿线为真值底盘路径，红点为订阅到的底盘路径。
- `trajectory.csv`：仿真时间、比赛系真值三维位置、订阅位置、位置误差；这是诊断文件，不是九列提交 CSV。
- `source/47_slam_map.pgm/yaml`：`camera_init` 源地图。
- `competition/47_map.pgm/yaml`：转换到比赛起点系的测试地图。
- 四个节点的参数快照和 `.log`，以及本场景 `result.json`；异常时附 `failure.log`。

产物都在 gitignore 的 `build/offline/` 内，不提交。

## 5 后续怎样覆盖 Point-LIO

先取得与 NUC 一致的 Point-LIO ROS 2 版本和依赖，再回放获准记录的原始 MID360
雷达与 IMU 数据。不能只回放 `cloud_registered` 和里程计，否则仍绕过定位算法。
要核对实际 `livox_ros_driver2/msg/CustomMsg`、逐点时间、雷达/IMU 时钟、加速度
单位和固定外参。有独立轨迹真值时再统计定位误差；没有真值只评价集成、漂移
现象和可重复性。

若需要系统扫描噪声、运动畸变和退化工况，再接入能输出匹配原始测量的三维
仿真器。是否选择 Gazebo 或其他工具，应先用最小数据样例确认能接入本机
Point-LIO 版本。当前结果不能替代现场静止漂移、已知距离、转向和返回起点测试。

工具机制参考：[ROS 2 时钟设计](https://design.ros2.org/articles/clock_and_time.html)、
[Point-LIO 官方说明](https://github.com/hku-mars/Point-LIO)。

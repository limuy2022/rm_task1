# 比赛启动与收尾

本页是**当前实机比赛链的唯一启动配方**。首次安装、编译和驱动准备见[整体部署](整体部署.md)；首次统一验收见[实验室统一验证](实验室统一验证.md)。相机由赛事方启动，本队一键启动MID360、唯一串口桥、Point-LIO、源建图、共享感知、比赛处理、控制和唯一提交器。比赛当天使用已验收配置，不临时编译。

## 1 启动前准备

- 仓库、编译安装及`.livox`均放在`~/ws_championship/src/43-rm_task1`内，按部署教程完成。实际装车参数保存为该目录的`vehicle43.yaml`；模板中的尺寸、角度不是实测结果。
- 本轮目标ID由主办方给定，0～49。现场已确定DICT_4X4_50、黑框外边长0.075m、相机YAML内参；不要改回10cm。
- 与主办方使用相同ROS域/RMW。脚本设置`ROS_LOCALHOST_ONLY=1`，保留现场`ROS_DOMAIN_ID`；正式运行不用演练域87。正式相机由主办方脚本启动，本队调试相机先停止。
- 停止此前的本队串口桥、Livox、LIO及处理/提交程序。一键入口自己启动它们，不能与单模块程序叠加运行。
- 主办方按其流程处理本轮输出；本队不删除、截断已有`43.csv`。所有调试记录放本队`records/`，不写主办方保护目录。

## 2 终端1：一条命令启动并保持运行

在NUC的Ubuntu终端执行，把示例ID `3`换成主办方指定值：

```bash
cd ~/ws_championship/src/43-rm_task1
bash tools/start_match.bash target_id:=3
```

脚本自动加载ROS、本队Livox与安装环境。网络JSON不存在时，按已确定的MID360、NUC `192.168.1.50`、雷达`192.168.1.3`生成；已存在的JSON保留。它不会改网卡、`.bashrc`或系统包。

启动后打印本次`records/match_XXXXXXXX`目录。日志在该目录的`ros_log/`，源地图在`source_map/`；准备完成后，实测整车参数快照为`vehicle_verified.yaml`。每次自动新建目录。

已验收的参数副本可这样指定，路径均用真实绝对路径：

```bash
bash tools/start_match.bash target_id:=3 \
  vehicle_config:="$HOME/ws_championship/src/43-rm_task1/vehicle43.yaml" \
  controller_params:="$HOME/ws_championship/src/43-rm_task1/controller43.yaml"
```

还可覆盖`camera_config`、`lio_config`、`livox_config`、`port`、`output_dir`；不传就用现场标准值。正式输出默认`~/ws_championship/output/43.csv`及`43_map.pgm/yaml`。比赛入口默认`motion_enabled=true`、`continuous=true`；准备完成后自动开始跟踪。只读调试可在启动时传`motion_enabled:=false`，也可显式覆盖`continuous`。

## 3 准备阶段：完成本次对齐并接入源图

入口先运行驱动、桥、LIO、源建图及**一份**检测器/PnP。准备未完成时不会开启控制和评分处理，不会自动猜尺寸、机械零位、工作区间或世界对齐；本场地面按已授权的高度近似计算。

另开终端2加载同一环境，保留现场域设置：

```bash
source /opt/ros/humble/setup.bash
TRACK_WS="$HOME/ws_championship/src/43-rm_task1"
source "$TRACK_WS/.livox/env.bash"
source "$TRACK_WS/install/local_setup.bash"
export ROS_LOCALHOST_ONLY=1
cd "$TRACK_WS"
ros2 topic echo /team43/match_session --once \
  --qos-reliability reliable --qos-durability transient_local
```

状态包含`epoch`及当前等待原因。准备节点就绪后会退出，该状态不再由它持续发布；此后看主终端和控制器status。

### 3.1 本次上电世界对齐

桥每次启动或MCU复位会改变epoch，世界对齐须对应**当前仍运行的桥/LIO会话**。按[参数文档B3/B4](未确认参数说明与确认方法.md#b3-参考零位和工作范围先建立能重复找到的姿态)摆到有依据的参考姿态、采参考和复核两份数据，按B4.6计算并复核，然后写入`vehicle43.yaml`的`kinematics.odom_world_rpy`、`calibrated_epoch`及确有测量依据的确认项。第一次只采数据交回分析时，入口继续等待是正常的，尚不能进入完整比赛链。

本入口已经启动桥、LIO与感知，执行B4时**跳过B4.1/B4.2的启动命令**，直接复用本次会话采样。准备阶段不提供位置保持或图像电机控制，参考姿态采用已验证的人工/固件保持方式；首次需要图像辅助调整时先按台架教程完成，不在此处另开第二个桥。绝不能只把旧配置的epoch数字改成当前数字来绕过世界对齐。

两轴区间采用B3已验证、留有线缆余量的工作区间，不要求碰撞机械端点。填入`yaw_limits_rad`、`pitch_limits_rad`，并在确认依据后设置`kinematics.joint_limits_confirmed: true`。用户提供的“俯仰最高约80°、水平小于180°”不能直接变成±80°。

### 3.2 本场直接采用斜装调平与高度近似，不要求点地面

用户已授权跳过RViz点地面。实机LIO配置使用本次静止IMU测得的`output_world_up=[-0.0321952086,-0.6955923471,0.7122368773]`，把算法原始世界系调平后再发布**位姿和点云两者**，frame仍为lio_world。原始驱动坐标及内部extrinsic_R/T不变。

配套建图入口读取同一份LIO配置：`approximate_floor_from_height=true`、`lidar_height_m=0.231`，自动得到`floor_z≈-0.182833m`并开始接收扫描，status注明`floor_source=height_approximation`。此处floor_confirmed表示已确认采用这份近似依据，不表示已做地面点选或地图精度验收。

计算依据是初始IMU原点为世界原点，雷达光心高度近似为0.231m；内部光心偏移调平后的z约0.048167m，因此地面z为0.048167−0.231。23.1cm原测量点未精确对应光心，仍有高度系统偏差；本方案按用户要求先采用近似。不同安装或高度变化时修改依据，不直接保留这组固定调平向量。

无需手动设置floor_z或floor_confirmed。可查看一次状态：

```bash
ros2 topic echo /team43/cloud_mapping/status --once
```

应出现`floor_source: height_approximation`且有效扫描增加。准备节点在实测整车配置、当前epoch和新鲜源图都满足后，保存快照并自动启动处理、控制和评分，无需再次launch。模板确认项仍保持false；高度近似不能代替整车标定。

本次输出坐标定义改变，更新并重新构建后应从新LIO会话建新图，世界对齐也对应新会话；不拼接更新前后的源图。如果主动选择人工地面方案，单模块建图入口仍可用`floor_z:=实际值 floor_confirmed:=true`明确覆盖。

## 4 就绪后：自动连续跟踪

默认启动时，主终端出现“准备完成；motion_enabled=true，continuous=true”。控制器自动开启，指定码及新鲜IMU、关节反馈到达后开始跟踪，无需再手动设置true。

```bash
ros2 topic echo /team43_tracking/status --once
```

应看到`operating_mode: match`、`continuous: true`；目标可见且反馈齐全时显示“跟踪中”。比赛模式按实测关节区间保护，两端默认各留0.035rad（约2°）余量，靠近边界挡住朝外速度，允许向内恢复。缺少新鲜图像、IMU、关节反馈或epoch不匹配时仍会停止。

只读采样、标定或准备低速试验时，启动命令明确关闭自动运动：

```bash
bash tools/start_match.bash target_id:=0 motion_enabled:=false
```

之后需要开启时执行：

```bash
ros2 param set /team43_tracking/visual_servo_node motion_enabled true
```

运行中可随时设false停止。故障锁停后先关闭运动、解决原因，再重新开启；continuous不会绕过故障和关节保护。

## 5 正式开赛与结果采集

必须在本轮`replay_start`之前让整条链持续接收底盘位姿。主办方发起本轮后，程序按该信号的stamp冻结比赛起点，开始逐tick写九列CSV。起点前等待map/目标世界位置是正常现象，不向`/judge/*`发送测试消息。

终端2可隔几秒观察一次：

```bash
wc -l "$HOME/ws_championship/output/43.csv"
```

行数应增长，主终端不能持续报告状态缺失、时钟异常或端到端迟到。计时诊断同时包含接收前排队和写出回调；NUC是否满足60ms本地余量由[实验室清单](实验室统一验证.md)中的独立读者确认。

一轮结束先关闭运动，保持整组程序运行到主办方完成文件采集；最后tick后0.7秒触发地图补存，watchdog周期0.2秒，不能看到最后一行就立刻Ctrl+C。中途停拍后恢复或地图更新会重新安排最终保存。

## 6 停止与归档

随时在终端2关闭运动：

```bash
ros2 param set /team43_tracking/visual_servo_node motion_enabled false
```

参数终端无法联系节点时，在**终端1**按Ctrl+C停止整组程序；实物异常由现场人员使用停机手段。关键进程退出会结束整组链；真实电机停转仍取决于固件与机械，必须先验收。停止echo的Ctrl+C只停止查看。

主办方采集完成后，在终端1 Ctrl+C。另执行只读检查并将文件复制到本次records目录留档，路径换为启动时打印的实际目录：

```bash
python3 -B tools/check_csv.py "$HOME/ws_championship/output/43.csv" --expected-rows 1800
ls -lh "$HOME/ws_championship/output/43.csv" \
  "$HOME/ws_championship/output/43_map.pgm" "$HOME/ws_championship/output/43_map.yaml"
MATCH_RUN="$TRACK_WS/records/实际match目录"
mkdir -p "$MATCH_RUN/submission"
cp "$HOME/ws_championship/output/43.csv" \
   "$HOME/ws_championship/output/43_map.pgm" \
   "$HOME/ws_championship/output/43_map.yaml" "$MATCH_RUN/submission/"
```

1800行为180秒10Hz完整轮次；中止轮次按实际tick数核对。失败文件保留，不修补CSV。下一轮重新启动本入口，取得新的桥/LIO会话、完成相应对齐与地面确认；正式输出清理由主办方负责。

## 7 只针对具体故障排查

| 现象 | 处理 |
|---|---|
| 等待实测配置/epoch | 看等待原因；文件路径、对应本次会话的B4结果及工作区间确认；不把模板全改true |
| 等待源图 | 查看height_approximation来源及建图status，LIO应持续输出；不重复开第二份驱动 |
| LIO无输出 | 看驱动/网络与PointCloud2拒收错误；默认已统一现场带前缀话题，不再选择消息类型 |
| 关节反馈中断/越界 | 先关闭运动，查实测几何、世界对齐、时钟、位姿间隙和工作区间；不靠放大超时或角度消错 |
| 串口打不开 | 查`/dev/ttyUSB0`及是否有旧桥占用；不要并行启动第二个桥 |
| 开赛后等待原点 | 起点stamp是否有历史底盘位姿覆盖、域/QoS是否与主办方一致；不能用最新位姿代替 |
| CSV不增长/节点退出 | 主终端tick、写出权限及单写者锁错误；不删除文件解锁 |
| 持续端到端迟到 | 保存完整日志与独立读者结果，按实验室负载验证处理；回调快不代表没有排队 |
| 地图没更新 | 源图→比赛map变换→`/map/grid`→保存日志；不能给源图改名冒充正式图 |

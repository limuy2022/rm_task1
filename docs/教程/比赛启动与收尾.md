# 比赛启动与收尾

当前走廊方案：**下午直接启动 LIO、视觉跟踪和 CSV 提交；不加载上午旧地图，不要求车辆回到原位，不等待地图重定位。** 用户确认栅格地图不参与评分、建议速度只用于输出，因此地图不再作为评分链的前置条件。

本队目录为 `~/ws_championship/src/43-MyDuo`。先按[整体部署](整体部署.md)上传并定向编译安装最新本队包。Livox驱动仍由本队入口启动，相机由赛事方启动。

## 1 上午地图与走廊模型

已经完成的两次地图原件保留，不用重做。两图拟合的侧墙间距分别约2.500m、2.487m，当前模型估计宽度2.494m，配置随 `team43_grid_mapper/config/corridor_model.yaml` 安装。它不是实测长度或独立精度验收。

下午不查找 `maps/current`，也不需要上传截断的原始录制。模型宽度仅用于筛选下午真实点云中的两条长墙，不能确定门、端点或车辆纵向位置；LIO独立计算运动。

需要另外采图时，仍可用 `bash tools/start_mapping.bash`，结束前另开终端 `bash tools/save_mapping.bash`；原始录制见[录制指南](原始数据录制与离线建图.md)。这些工具不需要在下午同时运行。

## 2 下午：一键启动

确认上午建图程序和其他雷达/LIO实例已经停止。**底盘静止，相机水平朝车头**，运行：

```bash
cd ~/ws_championship/src/43-MyDuo
bash tools/start_match.bash
```

默认 `motion_enabled=true`、`continuous=true`、`target_id=-1`。保持静止等待LIO位姿输出和首次云台世界参考对齐完成。未指定目标时不应主动跟踪其他码。

默认 `map_mode=corridor`：

- 不启动 `saved_map_node`，没有 `/initialpose` 或旧图匹配操作。
- 从当前配准点云拟合两条平行墙，连续三次一致后发布示意图；不会修改LIO位姿或正式起点。
- 看不见两侧长墙、地图节点退出或尚无地图，不影响目标/底盘/建议速度及CSV链。
- 建议速度先朝目标当前位置计算，再用实时配准点云限制朝障碍的速度，必要时转向或归零。保留限速、近距离停止、目标丢失和底盘/目标过期归零，不向底盘发送控制指令。

云台反馈、限位、运行中复位和传感器新鲜度保护仍生效。看到旧图缺失不需要补路径；默认流程根本不读取旧图。

### 实时防撞建议默认开启

不需要额外启动命令。`corridor` 和 `none` 两种比赛模式均默认开启实时障碍保护，直接订阅已有LIO的 `/red_standard_robot1/cloud_registered`，按正式TF变换到比赛坐标系；不依赖两线地图或旧图重定位。

- 用户给出底盘长宽约20～30cm，暂按两边均30cm取外接圆，并预留余量：中心到障碍保护距离为0.40m。该尺寸是近似值，不是实物验收。
- 筛选近似地面以上0.15～1.8m的回波，按圆形车体检查前瞻1.5秒的扫掠区域；点云离散误差另计入保护半径。模型假设的减速度为0.5m/s²，仅用于限制建议值，不代表已测实际制动能力。
- 直行方向不合适时，减速或在朝目标的前方半平面内选择偏转方向；均受阻则零速。速度下限不会在保护后将速度重新放大。
- 不只检查两侧墙，也检查点云中实际看到的端墙、关闭门扇及其他符合高度范围的障碍。未看到或低于15cm的障碍不在此检测保证范围内。
- 点云超过0.5秒未更新、点数不足、地面或TF不可用、消息损坏时建议归零；恢复有效数据后自动恢复。不会关闭CSV或要求人工确认。

底盘由主办方控制，本程序只能输出受约束的建议速度，不能实际刹车或保证底盘按建议行驶。现场首次使用应检查近墙时的建议方向，尤其确认底盘实际外廓没有超过上述近似。

## 3 裁判给目标ID后

等启动参考对齐完成，再在另一终端执行，以下以ID 0为例：

```bash
cd ~/ws_championship/src/43-MyDuo
bash tools/set_target.bash 0
```

检测器和PnP的ID读回应一致，随后自动连续跟踪，无需另外开启运动。检查相机确实看到指定码，底盘定位持续输出。车头大致朝向目标只供操作参考；程序继续通过实际底盘、云台姿态换算目标坐标，不将相机朝向等同于底盘车头。

## 4 通知裁判开赛，观察CSV

**指定码跟踪正确、LIO位姿和底盘定位正常、云台参考对齐完成后**，按裁判安排启动本轮客户端。比赛主终端全程保持运行，不需要等待走廊示意图。

以本轮有效 `/judge/replay_start` 的stamp建立比赛坐标原点：开赛时底盘中心为原点、车头为x轴、左侧为y轴。底盘位移由LIO计算，雷达位姿仍按安装外参换算到底盘中心。保留旧锁存起点过滤，不用tick代替比赛起点。

每个 `/judge/tick` 立即写九列CSV并刷新，时间取该拍stamp保留六位小数。客户端开赛删除旧CSV已有处理；首拍前没有CSV正常，不用手工建文件。

```bash
wc -l ~/ws_championship/output/43.csv
```

行数应随节拍增加；15分钟是现场窗口，程序不自行在180秒或1800行停止。若完整15分钟均10Hz发拍，约9000行，以实际收到的拍数为准。

起点与第0拍回调可能先后不同；刚开赛状态未就绪时仍可能降级写零，不能把这些零当成真实目标位置。没有地图不再引起建议速度无效，但有效底盘/目标状态及新鲜的实时障碍点云仍是必要输入；点云无效时建议归零，CSV继续写。

## 5 简化地图是什么，什么时候保存

若当前点云能形成两条侧墙，会发布 `/team43/slam_map`，随后按正式起点转换并由提交器写出：

```text
~/ws_championship/output/43_map.pgm
~/ws_championship/output/43_map.yaml
```

这是**平行墙几何示意**：墙间区域按模型填充；40m是显示窗口长度，不是测得的两门间距离；没有虚构端墙，不包含门扇和全部临时障碍。它不参与LIO定位或建议速度。实际模型及用途记录在本轮 `records/match_XXXXXXXX/corridor_model.json`。

看不到两侧墙时，可能没有上述地图文件；这不阻止CSV输出。用户确认地图不参与评分，本轮结果首先检查CSV，不拿上轮残留地图当作本轮已生成。

需要查看可选模型时，新终端加载环境：

```bash
source /opt/ros/humble/setup.bash
source .livox/env.bash
source install/local_setup.bash
export ROS_LOCALHOST_ONLY=1
ros2 topic echo /team43/corridor/status --qos-durability transient_local
```

此操作不是开赛必做步骤。

## 6 比赛结束与停车

需要立即关闭云台运动时，在加载上述环境的终端执行：

```bash
ros2 param set --no-daemon /team43_tracking/visual_servo_node motion_enabled false
```

裁判停止发拍后，确认 `43.csv` 存在且行数符合收到的拍数，在主终端 **Ctrl+C**。串口桥退出补发零速，真实电机制动仍以现场状态为准。保留正式output、本轮records及上午地图原件，不自行删除提交文件。

新一轮重新启动下午程序，静止完成参考对齐；不需要旧图重定位。轮次清理由主办方流程决定。

## 7 可选参数

- 完全不生成地图：`bash tools/start_match.bash map_mode:=none`。评分链和直接建议速度相同。
- 只读检查：加 `motion_enabled:=false`。
- 其他装车/相机/串口配置：`vehicle_config:=...`、`camera_config:=...`、`port:=...`。
- 实验室真实建图入口仍保留 `map_mode:=live`；旧图匹配实验需显式 `map_mode:=saved map_yaml:=/绝对路径/43_slam_map.yaml`。这两种实验模式继续使用地图规划建议速度，不是本次默认比赛方案。

# 比赛启动与收尾

本页给 B 在 NoMachine 连接后的 **NUC Ubuntu 终端**照顺序操作。A 核对目标、外参和结果，C 观察机构、电线并负责现场停机。首次方向与停止试验先完成[云台跟踪](云台跟踪.md)，部署和编译先完成[整体部署](整体部署.md)。比赛当天不临时编译或调高增益。

相机、K/D、串口、IMU 轴与单位直接沿用[现场已知前提](../记录/现场已知前提.md)，不再逐项执行 topic/type/hz/参数查询。首次验收完成后同一配置直接运行；本页只保留本轮会变化的状态观察。雷达建图的三阶段关系、源图与正式地图归属及详细地面操作统一见[底盘定位与点云建图](底盘定位与点云建图.md)。

本队定位接收层已支持 Livox 官方 PointCloud2；以下命令直接沿用 record3 的带前缀话题，不调整主办方驱动，不要求改发 CustomMsg。默认 `lidar_format:=auto` 自动识别发布者类型，驱动晚启动时等待；日志会显示实际选择。程序自动校验必需字段和布局，异常时明确拒收；无需赛前逐项手查 fields。实测装车参数和 NUC 正式提交链仍须完成首次验收。

首次补齐外参、接口和运行范围等依据时，从[参数文档附录B的B0操作准备](未确认参数说明与确认方法.md#附录-b-剩余数据的现场测量与交接)开始，按终端、姿态、采样、读包、地面点选和打包步骤执行；同一配置已经确认的项目不每轮重复。

## 1 启动哪几份程序

| 终端   | 保持运行的程序                                       | 职责                                     |
| ---- | --------------------------------------------- | -------------------------------------- |
| 现场已有 | 相机、Livox 驱动                                   | 提供图像、原始点云与雷达 IMU；沿用现场确认的驱动             |
| 1    | `visual_tracking.launch.py with_bridge:=true` | 图像跟踪、唯一 C++ 串口桥、云台 IMU 反馈；默认不转动        |
| 2    | `team43_lio_backend lio.launch.py`            | 自有 Small Point-LIO 定位和世界系点云            |
| 3    | `cloud_mapping.launch.py`                     | lio_world 中的源地图，确认地面后工作              |
| 4    | `processing.launch.py submission:=true`       | 底盘中心换算、比赛起点、云台运动学、目标预测、地图转换、方向建议、唯一提交器 |
| 5    | 参数和只读检查                                       | 开启/停止运动、检查状态与文件，不持续运行大量 echo           |

不要再开 `hardware_interface`、`bearing_*`、独立 `submission` 或旧 `competition/sim/mapping` 入口。同一串口只留一个桥，底盘和云台 TF 由处理链生成；当前 visual_tracking 桥已关闭自己的 TF。两条感知链分别使用 `/team43_tracking/*` 和 `/perception/*`，可以共享 `/image_raw`。

## 2 每个终端先加载同一环境

先保留现场已确认的 `ROS_DOMAIN_ID`、通信范围和 RMW 设置，所有终端一致，必须与驱动、评分端互通。**正式比赛不要沿用评分演练的域 87。**部署教程的 `ROS_LOCALHOST_ONLY=1` 只适合同机通信；跨机时按现场约定统一设置。

每个新终端都执行：

```bash
source /opt/ros/humble/setup.bash
# 此处先 source 现场已确认的 Livox 工作区 install/setup.bash
TRACK_WS="$HOME/team43_ws/rm_task1"
source "$TRACK_WS/install/local_setup.bash"
cd "$TRACK_WS"
TARGET_ID=0
VEHICLE_CONFIG="$TRACK_WS/vehicle43.yaml"
LIO_CONFIG="$(ros2 pkg prefix team43_lio_backend)/share/team43_lio_backend/config/small_point_lio_mid360.yaml"
CAMERA_CONFIG="$(ros2 pkg prefix team43_bringup)/share/team43_bringup/config/camera_team43.yaml"
OUT_DIR="$HOME/ws_championship/output"
```

`TARGET_ID=0` 是示例，各终端统一改成当场指定的 ID（0～49）。默认 -1 是等待选择，不跟踪任意码。包路径必须位于本队 `rm_task1/install/`。如有已验收的 LIO/相机配置副本，各终端把变量改成同一份绝对路径，启动命令使用所选文件。

相机沿用 `/image_raw`、1440×1080、rgb8 和 YAML 内参，串口使用 `/dev/ttyUSB0`，雷达 IMU 沿用 `/red_standard_robot1/livox/imu`。环境设置只在部署或通信异常时核对，不在五个终端重复查询。正式输出由主办方按轮次处理；不要手工删除或截断已有提交，也不要向 `/judge/*` 发测试消息。

## 3 终端 1：启动唯一跟踪程序与串口桥

已停止本队旧桥后执行：

```bash
ros2 launch team43_bringup visual_tracking.launch.py \
  target_id:="$TARGET_ID" with_bridge:=true port:=/dev/ttyUSB0 \
  camera_config:="$CAMERA_CONFIG"
```

如果已保存并验收了 PID 参数，同一命令追加 `controller_params:=实际YAML绝对路径`，保存方法见[调参检查清单](上机调参检查清单.md#3-调好了怎么保存下次怎样恢复)。每次启动仍强制 `motion_enabled=false`。

终端 5：

```bash
ros2 topic echo /team43_tracking/status --once
ros2 topic echo /task1/gimbal_reset_epoch --once \
  --qos-reliability reliable --qos-durability transient_local
```

指定码可见时 status 有对应 ID 和像素偏差，此时保持“只看不动”。status 正常就不另查 IMU 类型、频率或轴参数。记下 epoch。**从现在到本轮结束尽量保持终端 1 不重启**：桥每次启动、检测到 MCU 复位都会更新 epoch；epoch与对齐记录不一致时，需要重新完成本次会话的世界对齐。

## 4 终端 2：启动定位，完成本次上电对齐

```bash
ros2 launch team43_lio_backend lio.launch.py \
  params_file:="$LIO_CONFIG" lidar_format:=auto \
  lidar_topic:=/red_standard_robot1/livox/lidar imu_topic:=/red_standard_robot1/livox/imu
```

保持定位运行，位姿输出为 `lio_world → body`，body 是 IMU 参考点，底盘中心换算交给处理链。首次定位漂移验收在赛前完成，不每轮再静止采 30 秒；下节源地图正常接受扫描即可同时观察到定位与点云链已工作。

A/C 按[坐标外参与整车接入第 4、6、7 节](坐标外参与整车接入.md)完成本次静止同步对齐，B 将结果写入 `vehicle43.yaml`。重点核对：

- 安装外参、零位和限位沿用装车验收后的配置，不每轮重新量。
- `kinematics.calibrated_epoch` 等于终端 1 当前 epoch；`odom_world_rpy` 来自本次对齐。
- 底盘源为真实 odom，原点模式为 `judge_replay_start`；源地图为 `/team43/slam_map`，源 frame 为 `lio_world`。
- `grid.out_dir` 用本队独立目录（例如 `$HOME/team43_ws/rm_task1/maps_match` 的**实际绝对路径**），与正式 `OUT_DIR` 分开。YAML 不会展开 `$TRACK_WS` 这类 shell 变量。

原始 `vehicle_template.yaml` 会被启动校验拒绝。不能为了通过检查把所有 false 直接改为 true。

## 5 终端 3：启动源地图，确认本轮地面

```bash
ros2 launch team43_bringup cloud_mapping.launch.py \
  lio_params_file:="$LIO_CONFIG" output_dir:="$TRACK_WS/maps_lio_world"
```

它与定位读取同一份固定雷达↔IMU 外参。地面只在本次 LIO 初始化后测一次；同一 LIO 会话内重开建图，可把已测值作为 `floor_z:=实测值 floor_confirmed:=true` 传入，跳过重新点地面。

此时等待地面确认是正常的。按[建图教程第 4 节](底盘定位与点云建图.md#4-c-在-rviz-点地面-b-录入读到的高度)，在 RViz 的 `lio_world` 系量三个地面点的 z，取中间值。B 录入**本轮实测值**，例如实测确为 -0.79 时才输入：

```bash
ros2 param set /team43/cloud_mapping_node floor_z -0.79
ros2 param set /team43/cloud_mapping_node floor_confirmed true
ros2 topic echo /team43/cloud_mapping/status --once
```

应开始接受扫描，free/occupied 计数随观测增长。已经接受扫描后发现地面值错，必须停止建图、换新输出目录并重启后重测。LIO 重启会改变源坐标，旧地面和旧地图也须重新建立。

## 6 终端 4：开赛前启动处理与正式提交

先确认主办方的本轮评分环境已就绪、旧轮输出按其流程处理完，且没有另一份 `judge_io_node`。然后执行：

```bash
ros2 launch team43_bringup processing.launch.py \
  vehicle_config:="$VEHICLE_CONFIG" camera_config:="$CAMERA_CONFIG" \
  target_id:="$TARGET_ID" submission:=true team_id:=43 output_dir:="$OUT_DIR"
```

按本页只启动一份处理链就包含唯一提交器，无需再查询完整节点清单、评分类型或每条 TF。终端 4 无启动错误并继续运行；如果报告 epoch、外参或数据缺失，按文末故障表针对性排查。

**处理链必须在本轮 replay_start 之前持续接收底盘位姿。**开赛前没有 map 或有效 map 目标状态可以是正常等待；开赛后才有起点可冻结。若日志显示旧轮起点已被冻结，先核对现场锁存的 replay_start，下一轮前按主办方流程重启处理链，不能带着旧起点等待新轮。

## 7 人工开启跟踪，然后等待正式开赛

方向、停止、参数与机构范围已实机验收后，由 B 在终端 5 输入：

```bash
ros2 param set /team43_tracking/visual_servo_node motion_enabled false
ros2 param set /team43_tracking/visual_servo_node axes both
ros2 param set /team43_tracking/visual_servo_node continuous true
ros2 param set /team43_tracking/visual_servo_node motion_enabled true
ros2 topic echo /team43_tracking/status --once
```

每条 set 须成功，status 应显示跟踪中且偏差减小。增益、方向和速度采用已验收值。`continuous=true` 只取消 15 秒试转时间窗，仍保留相对启动姿态 `max_rotation`（默认约 20°）和 IMU/图像/复位保护；当前图像控制不能据此宣称覆盖全场大角度追踪。比赛所需范围须提前实机验收，不在现场直接放宽限制。

主办方发布本轮 `/judge/replay_start` 和 `/judge/tick` 后，终端 4 应报告按对应 stamp 冻结比赛原点，并逐拍写 CSV。终端 5 只看本轮是否开始产出：

```bash
wc -l "$OUT_DIR/43.csv"
```

隔几秒再看，行数应增长，终端 4 不应持续报状态缺失/过期。正常运行不再逐条 echo 目标、底盘、建议速度和地图或启动 tf2_echo。CSV 增长只说明正在写出，定位/预测精度由赛前验收负责；异常时才按下表排查。

## 8 停止、收尾与下一轮

随时停止云台，在终端 5 输入：

```bash
ros2 param set /team43_tracking/visual_servo_node motion_enabled false
```

参数终端无法联系节点时，在终端 1 Ctrl+C；异常运动由 C 采用现场停机手段。停止 echo 的 Ctrl+C 只停止查看，不会停止跟踪。正常结束时先关闭运动，**保留终端 4 到主办方完成结果采集**：提交器在 tick 停止后尝试保存最后地图，不能刚到 180 秒就关闭整组程序。

采集结束后只读核对：

```bash
ls -lh "$OUT_DIR/43.csv" "$OUT_DIR/43_map.pgm" "$OUT_DIR/43_map.yaml"
python3 -B "$TRACK_WS/tools/check_csv.py" "$OUT_DIR/43.csv" --expected-rows 1800
```

1800 行用于完整 180 秒、10 Hz 的轮次；中止或实际拍数不同须对照现场 tick 记录。检查器失败时保留输出，不修补 CSV。确认地图保存日志和地图 frame/内容，空文件或仅有旧文件不算成功。格式检查不能代替 NUC 延迟与真实精度验收。

待结果采集完成，在终端 4、3、2、1 依次 Ctrl+C，保留启动命令、配置、epoch、日志和本轮产物；不停止主办方驱动。下一轮前重启处理/提交链以清除旧起点和状态，并按主办方流程处理正式输出。若 LIO、桥或设备重启，分别重建源地图、重做相应世界对齐；不复用已失效的确认结果。

## 9 故障速查

| 现象 | 立即检查或处理 |
|---|---|
| LIO 无输出 | 使用默认 `lidar_format:=auto` 与记录中的带前缀话题；若显示“等待点云发布者”，查驱动/话题；若报类型冲突，按日志处理，选定后冲突须重启定位；若报“拒收 Livox PointCloud2”，保存具体字段/布局错误，再针对性读取 fields；不要切换主办方驱动 |
| 找不到包、消息类型无效 | 每个终端是否 source 同一安装空间，pkg prefix 是否指向本队版本 |
| 串口打不开或 IMU 不更新 | 终端 1 第一段错误、真实设备名、是否已有桥占用；不要另开桥抢占 |
| 只看不动、跟踪十几秒就停 | status、motion_enabled、continuous；幅度/IMU/复位锁停先查原因，再人工 false→true |
| 朝反方向转 | 立即停，按单轴教程核验符号；不要增大 PID |
| epoch 不匹配或关节无效 | 桥/MCU 是否重启，本次对齐与 calibrated_epoch 是否仍有效 |
| 等地面、源地图无有效扫描 | 地面是否实测确认，点云和位姿是否更新，LIO 配置是否一致 |
| 开赛后仍等待起点、TF 不完整 | replay_start 的 stamp 是否被已缓存底盘位姿覆盖，域/QoS 是否一致；不造单位阵或补发起点 |
| CSV 无增长或提交器退出 | tick 订阅、终端 4 日志、输出权限、单写者锁；不要删除文件解锁 |
| CSV 中断后想重启 | 保留文件；写出器可校验既有行并去重追加，但 tick 不会自动补齐，处理链也可能已丢开赛历史；不能视为无损恢复 |
| 地图文件没有更新 | `/team43/slam_map` → map TF → `/map/grid` → 提交器保存日志逐段查，不拿源地图改名顶替 |

首次准备与专项排查分别见[整体部署](整体部署.md)、[云台跟踪](云台跟踪.md)、[装车外参](坐标外参与整车接入.md)、[定位建图](底盘定位与点云建图.md)；合成提交演练见[评分接口测试](评分接口测试.md)。

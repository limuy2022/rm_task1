# 完整项目上传与部署

部署单位是整个 `rm_task1` 仓库，比赛机上放在题目指定的本队目录 `43-MyDuo`。源码、配置、文档、工具、第三方子模块与 vendor
源码一起传输；NUC 重新编译自己的包，不使用个人电脑的 build/install。

本轮近似装车配置vehicle_field.yaml已随bringup安装，启动入口固定默认使用它，无需额外参数；需要其他配置时显式传vehicle_config，详见比赛启动页。

配置文件按功能归属存放，路径与覆盖顺序见[配置文件归属](配置文件归属.md)。

比赛当天的终端顺序与收尾统一见[比赛启动与收尾](比赛启动与收尾.md)；本页只处理部署。

## Git 交接

1. 在自己的仓库核对 `git status` 和差异，只提交本次源码、配置和文档；不提交 build/install/log、压缩包或实验产物。
2. commit message 用中文并带 conventional 前缀，例如 `docs: 整理比赛启动手册`。提交后推送，接收方拉取同一提交并检出子模块；GitHub Desktop 可用 Changes → Commit → Push，接收方 Fetch → Pull。
3. 接收方须有私有仓库权限。双方记录同一 commit；遇到冲突先核对差异，不整份覆盖。NUC 使用下面的完整归档流程，不传个人电脑的编译产物。

## 准备完整源码归档

在个人电脑的项目根目录先检出子模块：

```bash
git submodule update --init --recursive
```

可以用压缩软件归档整个项目，也可以在 Linux/macOS 的项目根目录执行：

```bash
tar --exclude=.git --exclude=build --exclude=install --exclude=log \
  --exclude=__pycache__ --exclude=.pytest_cache --exclude=.venv --exclude=.livox \
  --exclude=output --exclude=outputs --exclude=maps --exclude=records \
  --exclude=MvSdkLog --exclude=.DS_Store \
  --exclude='*.zip' --exclude='*.bag' --exclude='*.db3' --exclude='*.mcap' \
  -czf /tmp/team43.tar.gz .
```

保留仓库自带的 `archives/`、子模块和 vendor，不要把必要依赖当作实验产物排除。
上传前确认其中包含 `src/`、`tools/`、`docs/` 和 `gimbal-edu-tools/`。

## 在 NUC 的本队目录构建

本队源码、配置和构建产物均放在题目允许的`~/ws_championship/src/43-MyDuo`。
在NoMachine的NUC终端先创建目录，再通过文件传输将归档上传到这个目录：

```bash
TRACK_WS="$HOME/ws_championship/src/43-MyDuo"
mkdir -p "$TRACK_WS"
```

上传完成后解压，并从仓库归档构建Livox；脚本只构建驱动，不启动硬件，不安装系统库：

```bash
tar -xzf "$TRACK_WS/team43.tar.gz" -C "$TRACK_WS"
cd "$TRACK_WS"
bash tools/build_livox.bash
```

驱动源码和产物位于本队`.livox/`下。脚本校验归档哈希，生成`.livox/env.bash`，同时加载
ROS安装空间和SDK动态库路径。不要只source驱动的install而漏掉SDK库。
若构建缺少系统依赖，保留第一个报错交现场处理，不用pip覆盖ROS库。

然后定向构建本队项目：

```bash
source /opt/ros/humble/setup.bash
source "$TRACK_WS/.livox/env.bash"
colcon --log-base "$TRACK_WS/log" build --base-paths "$TRACK_WS/src" \
  --build-base "$TRACK_WS/build" --install-base "$TRACK_WS/install" \
  --cmake-args -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
source "$TRACK_WS/install/local_setup.bash"
ros2 pkg prefix team43_control
ros2 pkg prefix livox_ros_driver2
```

本队包路径应在`43-MyDuo/install/`，Livox路径应在`43-MyDuo/.livox/install/`。
不在公共工作区根目录全量构建，不修改`.bashrc`或主办方保护目录。
开发验证仍按[测试运行指南](测试运行指南.md)在Docker的`/workspace`中运行。

## 雷达驱动由谁启动

按[题目原文](../赛题原文.md)，选手负责配置并启动`livox_ros_driver2`。
[校内赛环境页](https://blog.secaumene.com/kit/campus-contest-env.html)已经明确：

| 项目 | 本场环境 |
|---|---|
| 雷达 | Livox MID360 |
| 雷达IP | `192.168.1.3` |
| NUC接收IP | `192.168.1.50` |
| 选手个人电脑IP | `192.168.1.25`；不是雷达数据接收地址 |
| 网络 | 主办方已配好；驱动在NUC运行，不在个人电脑运行 |
| ROS通信 | 保持`ROS_LOCALHOST_ONLY=1`，与评分系统一致 |

本队提供`livox.launch.py`，只启动一份硬件驱动，发布
`/red_standard_robot1/livox/lidar`和`/red_standard_robot1/livox/imu`。
云台IMU `/red_standard_robot1/gimbal`由本队串口桥发布，不能由雷达IMU代替。

首次加载下面的环境后生成本场配置：

```bash
ros2 run team43_bringup configure_livox \
  --output "$TRACK_WS/config/livox_mid360.json"
```

默认使用上表型号与地址，端口沿用配套驱动的MID360定义。生成器不修改网卡、不连接设备，
且拒绝覆盖已有文件。若现场明确换了地址，可显式追加`--host-ip`与`--lidar-ip`，输出到新文件。
驱动JSON中的`extrinsic_parameter`保持全零以输出原始雷达坐标；雷达到内部IMU的固定外参只在LIO中应用。

在一个独立的雷达驱动终端加载环境后执行，保持运行：

```bash
ros2 launch team43_bringup livox.launch.py \
  config_file:="$TRACK_WS/config/livox_mid360.json"
```

驱动固定`xfer_format=0`，只发布PointCloud2；定位端直接订阅同一格式，
不提供格式选择或自动识别参数。驱动launch不启动电机、相机或LIO。

运行顺序为：**Livox驱动 → LIO → 源建图 → 比赛处理与提交**。
驱动已由本队启动且输出正常时复用该实例，不再启动第二份。
SDK库错误先核对`.livox/env.bash`是否加载；无数据再核对网络和配置，不把source环境当成启动驱动。

## 加载环境

每个新终端先加载 ROS、同一份现场 Livox 环境，再加载本项目：

```bash
source /opt/ros/humble/setup.bash
TRACK_WS="$HOME/ws_championship/src/43-MyDuo"
source "$TRACK_WS/.livox/env.bash"
source "$TRACK_WS/install/local_setup.bash"
export ROS_LOCALHOST_ONLY=1
```

然后按[比赛启动与收尾](比赛启动与收尾.md)使用`bash tools/start_match.bash target_id:=本轮ID`启动整条实机链；首次按[实验室统一验证](实验室统一验证.md)验收。首次试转、标定和隔离域评分演练从该页链接进入。
完整上传不代表同时启动所有入口；共享的相机、雷达和串口桥各保留一份。
比赛入口直接启动全链，设置目标ID后默认自动连续跟踪；只读采样或标定时传`motion_enabled:=false`。台架试转仍由参数终端显式开启。

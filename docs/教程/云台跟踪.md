# 在 NUC 上运行云台跟踪

目标：把指定 ArUco 码移到画面左、右、上、下，云台向目标转，画面偏差减小。相机、雷达沿用现场已经启动的驱动。以下命令由 B 在 Windows NoMachine 连接后的 **NUC Ubuntu 终端**输入。

## 1 三个人现场怎么配合

- B：在 Windows 打开 NoMachine，连接 NUC。本文所有 bash、ros2 命令都输入远程 Ubuntu 的终端，不输入 Windows PowerShell。负责传包、编译、启动和改参数。
- A：拿指定 ID 的码，按下面顺序移动；读 `error_px`，记录方向、收敛时间和增益。先用 ID 0，之后按实际指定 ID 修改。
- C：固定云台底座，观察电线和机械活动范围，准备现场停止手段。开始前让相机朝向码，离机械两端都有余量；不要靠带电手掰电机来找端点。

云台通信已经打通：串口 `/dev/ttyUSB0`，IMU 轴参数 `[1,1,1]`。本轮不重新找线、不重新标定、不重画 O/C 坐标。

## 2 上传完整项目并编译

按[整体部署教程](整体部署.md)把完整项目上传到 NUC 的 `~/team43_ws/rm_task1`，
只编译该目录中的本队包。源码、配置、工具和子模块随完整项目一起传输，不再生成云台专用精简包。

本文各终端先按整体部署教程加载 ROS、现场已有的 Livox 环境和本项目
`install/local_setup.bash`，设置 `TRACK_WS="$HOME/team43_ws/rm_task1"`。
不要在公用 `~/ws_championship` 根目录全量构建，不改 `.bashrc`，不启动第二份相机或雷达驱动。

编译失败时保留第一个报错及其上下各十行，先解决错误再继续。

## 3 第一次启动 只看结果 不转动

终端 1：

```bash
ros2 launch team43_bringup visual_tracking.launch.py target_id:=0
```

先用 `ros2 pkg prefix team43_control` 确认路径位于本项目的 `install/team43_control`，启动后应显示“图像PID就绪”。默认不开串口桥、不发速度，码移动时云台不会跟着动。

B 再开终端 2，输入：

```bash
source /opt/ros/humble/setup.bash
TRACK_WS="$HOME/team43_ws/rm_task1"
source "$TRACK_WS/install/local_setup.bash"
export ROS_LOCALHOST_ONLY=1
ros2 topic echo /team43_tracking/status --once
```

A 把 ID 0 的码放在相机前，距离约 1～2 米，完整露出黑色正方形，不遮角点。重复上一条 echo，应该看到类似：

```text
data: '{"state": "只看不动", "id": 0, ... "error_px": [80.0, -40.0], ...}'
```

数字只是示例。`error_px` 第一项是目标中心在光轴右边多少像素，第二项是在光轴下面多少像素。右/下为正；左/上为负。新内参的光轴落点约为 `(710,563)`，不强行用图像几何中心 `(720,540)`。[相机投影和 PnP 原理见官方第二课](https://blog.secaumene.com/teach/class-2.html)。

- `id: null` 或没有 `error_px`：还没看到指定码。先检查拿的是不是 ID 0、画面是否清楚。不要以此去重做标定。
- 要改 ID，最直接是在终端 1 Ctrl+C，再把启动命令中的 `target_id:=0` 改为实际 0/1/2/3。默认不指定 ID 时为 -1，等待选择，不会跟任意码。
- 完全没有 status：看终端 1 是否退出，把第一段错误发回来。
- 想看实时画面时可继续使用现场已有的 RViz 图像窗口；本入口不额外启动相机驱动。

## 4 切换到能转动的模式

B 在终端 1 按 Ctrl+C，停止刚才的观察程序。若之前另外开着你们自己的 `/robo_bridge`，回到它原来的终端 Ctrl+C；相机、雷达保持运行。**不要同时开两个桥读取 `/dev/ttyUSB0`，不要使用 pkill 杀一批进程。**

终端 1：

```bash
ros2 launch team43_bringup visual_tracking.launch.py target_id:=0 with_bridge:=true port:=/dev/ttyUSB0
```

这次增加真实串口桥，仍然默认 `motion_enabled=false`。桥把本程序的 Twist 速度变成 0x30 下发，IMU 继续发布到已确认的话题。帧格式和 rad/s 单位见[主办方串口协议](https://blog.secaumene.com/kit/protocol.html)。不需要刷固件，也没有额外电机驱动程序。

如果提示串口被占用，确认你们旧桥是否已在其终端停止；别占用别人正在使用的设备。若现场端口确实变了，先保留 `ls -l /dev/ttyUSB*` 输出再处理，不恢复使用已知无效的 `/dev/gimbal`。

B 同时看终端 1 的串口诊断。桥每秒通过 Linux `TIOCGICOUNT` 查询 UART 错误计数，首次成功查询只建立基线，不计入设备历史错误；本次有新增错误时输出 WARN：

```text
UART 错误增量：frame=... parity=... overrun=... brk=... buf_overrun=...
```

`frame` 是停止位等帧格式错误，`parity` 是奇偶校验错误，`overrun` 是硬件接收溢出，`brk` 是 break 条件，`buf_overrun` 是驱动接收缓冲区溢出。这些数值来自驱动，不是坏协议帧数。串口在 raw 配置基础上启用输入错误检查，让部分 CP210x 驱动能上报错误；仍为 8N1，不增加奇偶校验位，协议双校验继续生效。合法字节不变；驱动标记为 framing/parity 错误的字节会由 Linux 转成 NUL 后交给协议解析。出现增量时保存完整日志、启动命令和端口，结合协议错误、IMU 是否持续更新及接线排查，不先调 PID。

若 PTY 或驱动不支持查询，桥只输出一次 INFO 后继续收发；其他查询失败会限频 WARN 并继续重试，恢复后继续诊断。部分驱动直接不支持查询；另有部分驱动虽可查询，但未实现某些字段，部分 CP210x 兼容芯片也可能不提供错误事件，因此没有告警不代表链路健康。PTY 与查询结果注入测试只覆盖软件行为，真实停止位错误、硬件及驱动缓冲区溢出尚未上机验证。这项诊断不改变 `motion_enabled=false` 的默认状态，试转仍由 B 按下文显式开启。

终端 2 已经加载本项目环境，无需重做。关闭终端再开时，按整体部署教程重新加载环境。

### 4.1 只试左右 3 秒

A 把码放在光轴附近，偏右约 50～100 像素，别一开始放在画面边缘。C 观察底座、电线和可转范围。B 在终端 2 依次输入：

```bash
ros2 param set /team43_tracking/visual_servo_node axes yaw
ros2 param set /team43_tracking/visual_servo_node max_omega 0.08
ros2 param set /team43_tracking/visual_servo_node run_seconds 3.0
ros2 param set /team43_tracking/visual_servo_node motion_enabled true
```

每条应返回 `Set parameter successful`。相机应朝码的方向转：码在画面右边，相机向右转，`error_px` 第一项应向 0 接近；码在左边则反过来。这里 `.08 rad/s` 约为每秒 4.6 度，只试 3 秒。

要看指令和偏差，终端 2 输入：

```bash
ros2 topic echo /team43_tracking/status
```

`state: 跟踪中` 时会有 `yaw_omega`。默认符号下，画面右侧目标对应负 yaw，左侧对应正 yaw。3 秒后应显示“本次试转时间结束”，不会自行重启。终端 2 的 Ctrl+C 只是停止 echo，**不会关闭终端 1 的跟踪程序**。

**随时停止：**在终端 2 结束 echo 后输入：

```bash
ros2 param set /team43_tracking/visual_servo_node motion_enabled false
```

也可以在终端 1 Ctrl+C 停整组程序。程序请求停止时发三帧零速度，随后停止发指令，让下位机超时保护生效。协议描述的 0.5 秒减速、3.5 秒失能是固件约定，尚未测过实际制动时间；零指令不等于断电，异常时由 C 使用现场停机手段。

若越转偏差越大，立即停，**不要靠增大增益去补符号错误**。确认只错左右转向后，在关闭状态输入：

```bash
ros2 param set /team43_tracking/visual_servo_node yaw_sign -1.0
```

再开启三秒试转。如果仍然不对，保留现象和 status，不乱改 IMU 的 `[1,1,1]`。输出指令符号与 IMU 轴映射是两回事。

每次重新开始：先设 `motion_enabled false`，等一秒，再设 true。这样清除本次试转的状态、积分和时间限制。

### 4.2 只试上下 3 秒

B 先关 false，再输入：

```bash
ros2 param set /team43_tracking/visual_servo_node axes pitch
ros2 param set /team43_tracking/visual_servo_node motion_enabled true
```

A 把码放在光轴下方约 50～100 像素。相机应低头，`error_px` 第二项向 0 减小；码在上方应抬头。默认画面下方目标对应正 pitch 指令。若上下正好反了，先 false，在关闭状态把 `pitch_sign` 设 `-1.0`，再试。不要改已确认的 O/C 坐标定义。

### 4.3 两轴一起跟踪

两轴方向都正确后，先 false，然后输入：

```bash
ros2 param set /team43_tracking/visual_servo_node axes both
ros2 param set /team43_tracking/visual_servo_node max_omega 0.25
ros2 param set /team43_tracking/visual_servo_node run_seconds 15.0
ros2 param set /team43_tracking/visual_servo_node motion_enabled true
```

A 缓慢把码向左右、上下移动。云台应跟着转，码重新靠近光轴。当前只做小范围测试；单次姿态相对起点变化达到约 20 度会停。**这是试转幅度限制，不是机械限位。**启动点如果本来就靠机械端点，20 度并不安全，所以 C 仍需观察可动空间和电线。

### 4.4 持续跟踪

小范围跟踪验收后再用。持续模式只解除 `run_seconds` 时间窗，其余停转条件一个不少：相对启动姿态变化超过 `max_rotation`、丢图超时、云台 IMU 中断、串口桥复位，任一发生都会锁停并要求重新开关 `motion_enabled`。先 false，然后：

```bash
ros2 param set /team43_tracking/visual_servo_node continuous true
ros2 param set /team43_tracking/visual_servo_node motion_enabled true
```

持续模式不是无人值守模式：C 仍守在参数终端，随时 `motion_enabled false` 或在启动终端 Ctrl+C。`status` 里的 `continuous` 字段可确认当前模式；切回试转设 `continuous false` 后重新开闸。

## 5 怎么判断成功 怎样调参

先验收方向，再验收跟踪，不把“程序没报错”当成功。

1. 左右、上下四个方向，实际转向都让对应像素偏差减小。
2. 静止码从约 100 像素初始偏差开始，两轴模式下先以“5 秒内接近光轴、偏差约 10 像素内保持 3 秒”为现场调参目标。达不到就记下实际数值；这是我们的验收目标，不是已测性能。
3. 码缓慢移动时，画面偏差不持续增大，目标不反复甩出画面。
4. 遮住码后，最多两帧、总时长最多 80 ms 做速度衰减，随后停止，不继续朝盲区追；重新看到码可在本次时限内恢复。IMU中断、试转时间结束或姿态幅度超限会停止，需先 false 再 true。程序对图像和 IMU 的有效期默认 0.15 秒。
5. `motion_enabled=false` 和终端 1 Ctrl+C 都实际试一次，记录停止现象；不在第一轮进行大角度、快速甩动或自动搜索。


参数怎么改、怎么保存，单独看[上机调参检查清单](上机调参检查清单.md)。先完成方向与停止试验，再调速度和精度。

## 6 常见现象 该怎么做

| 看到什么 | 说明及操作 |
|---|---|
| `只看不动` | motion_enabled 仍为 false，是默认状态 |
| `等待指定码的新图像` | 拿对 ID，把完整码放到清晰画面中；如果已收到过图像又停止，检查图像是否停更 |
| `等待新云台IMU` | 真实模式下看终端1桥是否打开成功；已确认链路无需重建，优先排查旧桥占用或本次桥退出 |
| `云台IMU中断` | 本次运动锁定停止；恢复数据后先 false 再 true |
| `本次试转时间结束` | 正常到时，先 false 再 true 开始下一次 |
| `本次转动达到角度范围` | 正常达到本次幅度限制，先停下重新安排小范围试验，不直接放宽限制追码 |
| `Set parameter ... not found` | 终端1是否仍在运行？终端2是否 加载本项目 install/local_setup.bash？节点全名是否写对？ |
| `message type invalid` | 新开一个终端，加载本项目 install/local_setup.bash 后重试。不要重画坐标、重做标定；仍失败保留命令和完整错误 |
| 有非零速度但电机不转 | 查看桥是否启用了 with_bridge=true、终端1是否报串口错误；记录指令与硬件现象，不推断为 PID 参数错误 |


## 7 看画面和留下调参记录

### 7.1 怎么看图上有没有框 指令和偏差

先结束你自己的旧跟踪进程。终端 1 启动只观察模式：

```bash
ros2 launch team43_bringup visual_tracking.launch.py target_id:=0 with_debug:=true
```

B 在现场已有 RViz 中点击左下角 **Add → By display type → Image → OK**。点开新 Image 的属性：Image Topic 选 `/team43_tracking/debug_image`；若 QoS 属性可见，把 Reliability 设为 **Best Effort**。画面应出现黄色光轴十字、绿色目标框和 ID，以及误差、输出角速度、状态文字。文字用英文以避免 OpenCV 中文字体乱码：`raw px` 是原始像素偏差，`filtered deg` 是滤波后的角度偏差，`control deg` 是扣除死区后送进 PID 的偏差，`omega` 是实际请求的角速度。

这不是在原始图像上造新测量：输出图保留相机原时间戳，框和状态相差超过 80 ms 时不硬叠，超过 300 ms 的旧图不重新发布。调试绘图在单独进程，退出不会关闭跟踪控制器。画面不显示时先看 RViz 订阅 topic 和 Reliability，再看终端 1 有没有 Debug 提示；不要再启动一遍相机。

需要真实转动时，在同一命令末尾再加 `with_bridge:=true port:=/dev/ttyUSB0`，然后仍按第 4 节由人开启运动。`with_debug` 本身不会开启运动。

### 7.2 怎么保存误差和速度

停止你自己的跟踪进程后，在终端 1 启动（以下仍只看不动）：

```bash
ros2 launch team43_bringup visual_tracking.launch.py target_id:=0 with_debug:=true debug_csv:="$HOME/team43_ws/rm_task1/tracking_trial_01.csv"
```

应在该目录出现 `tracking_trial_01.csv`。观察器按状态消息频率记录，默认约 50 Hz，包含原图时间、记录时间、原始/滤波/控制偏差、丢失帧数和 yaw/pitch 速度，每行刷新。文件已存在时**不会覆盖**，终端会显示 `Debug CSV disabled`；下一次把 `01` 改为 `02`。写盘失败只关闭调试日志，不影响控制。这份 CSV 是调参记录，不是比赛的九列 CSV。

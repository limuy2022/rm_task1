# 评分接口：三个终端连续跑 180 秒

目的：先证明每拍能及时写出九列和刷新文件；它不证明定位精度。B 用自己的 Ubuntu，或 NUC 上的独立 ROS 域。不要在 Windows PowerShell 输入下面命令。

## 1 准备本次程序

在 B 自己的 Ubuntu，或者实验室 NUC 的独立 ROS 域执行。不需要相机、雷达或电机。本试验只发布 `/test/tick`、`/test/replay_start` 和合成内部状态，**不向 `/judge/*` 发布任何消息**。不要和真实处理节点放在同一个 ROS 域。

使用本次 **十一包版本** `47-visual-tracking`，其中已附评分包、地图写出工具和合成源。按[云台跟踪教程的传包/编译步骤](云台跟踪.md)传包、编译成功后即可，不另外创建评分工程。旧的六包版本不能用于本节。

### 1.1 打开三个新终端，选择 本次程序和测试域

B 在 NoMachine 里的 NUC Ubuntu 打开三个新终端。**三个终端分别输入同一段**：

```bash
source "$HOME/ws_championship/src/47-visual-tracking/use_here.bash"
export ROS_DOMAIN_ID=87
ros2 pkg prefix gimbal_judge_io
```

最后应显示路径结尾为 `47-visual-tracking/install/gimbal_judge_io`。`use_here.bash` 已设置 `ROS_LOCALHOST_ONLY=1` 和本次程序路径。域 87 留给本次试验；如果本机已有别人使用该域，三个终端一起换成另一空闲域。

然后**只在终端 1**检查测试输出目录：

```bash
if [ -e "$TRACK_WS/score_check_01" ]; then
  echo '旧测试目录已存在。先停止，不要沿用本轮输出；下次统一改用 score_check_02。'
else
  echo '测试目录尚不存在，可以继续。'
fi
```

应显示“测试目录尚不存在，可以继续”。若目录已存在，停在这里保留旧结果；重试时把下文终端 1、2、验收命令里的 `score_check_01` 全部改成新的 `score_check_02`。测试输出只写在我们 独立工作区目录内，不写正式 `~/ws_championship/output`。

### 1.2 三个终端依次运行

**终端 1：启动实际提交器，保持运行。**评分话题映射到 `/test/*`，只处理合成源。

```bash
ros2 launch gimbal_tracker_bringup submission.launch.py team_id:=47 output_dir:="$TRACK_WS/score_check_01" tick_topic:=/test/tick replay_topic:=/test/replay_start
```

**终端 2：先启动观察器，再启动数据源。**它等待 CSV 出现，记录每行第一次可见的时间。

```bash
python3 -B "$TRACK_WS/tools/observe_submission.py" "$TRACK_WS/score_check_01/47.csv" --count 1800 --timeout 240
```

**终端 3：最后启动固定数据源。**

```bash
python3 -B "$TRACK_WS/tools/submission_test_source.py" --count 1800
```

应等待订阅就绪，预热约 2 秒，再发 1800 拍，约 180 秒后收尾。数据源退出且观察器打印结果后，再在终端 1 按 Ctrl+C。任何终端出现错误先保留输出，不通过反复重启向同一 CSV 追加测试。

### 1.3 怎样判断成功

观察器应显示 `passed: true`、`rows: 1800`、`errors: []`、`partial_tail_bytes: 0`、`over_60ms: 0`。另运行：

```bash
wc -l "$TRACK_WS/score_check_01/47.csv"
head -n 1 "$TRACK_WS/score_check_01/47.csv"
ls "$TRACK_WS/score_check_01/47_map.pgm" "$TRACK_WS/score_check_01/47_map.yaml"
```

应正好 1800 行，无表头；每行前八列为 `1,2,1,2,0.5,-0.25,0.3,0.4` 的六位小数形式，最后一列是递增的 tick 时间，固定六位小数。这里目标静止，所以预测位置等于当前位置。地图是固定的 4×3 格测试地图，不是真实场地图。

| 现象 | 下一步 |
|---|---|
| 找不到包/消息类型无效 | 核对三个终端的 `ros2 pkg prefix gimbal_judge_io`；必须是 本次包内部的安装目录；确认编译过十一包版本 |
| 数据源等待订阅，30 秒后超时 | 核对三个终端域都是 87，终端 1 没退出，两条评分话题已映射为 `/test/*` |
| 观察器说 CSV 非空 | 已跑过这一轮；停止本轮，保留结果。重新试验必须使用新的输出目录，并同时改终端 1、2 的路径 |
| 少于 1800 行、有错误或延迟超标 | 保留三个终端输出和观察器 JSON；这时没有通过，不用“文件最终存在”代替验收 |

观察器采用 60 ms 作为预留余量的本地标准；官方迟到线是 80 ms。**截至本次交付，尚未用此试验证明 NUC 的 180 秒连续通信和 80 ms 时限。**规则依据见[官方比赛环境文档](https://blog.secaumene.com/kit/campus-contest-env.html)；这里只做合成数据验证，不产生正式提交。

验收和保存输出后，关闭这三个测试终端。不要直接在域 87 的旧终端启动真实跟踪；回到上机教程，另开终端重新 source 本次程序，保留现场原本的跟踪域。


## 2 想单独比较写盘性能时

下面不包含 ROS。当前 Mac 已实际跑满 180 秒/1800 行：漏拍 0，独立读者可见延迟平均 1.73 ms、最大 31.62 ms，≥80 ms 为 0。它是离线基线，不代替上一节的 NUC 消息链验收。完整结果保存在[离线基线 JSON](../验证/离线基线_R3_20261018.json)。

在已 source 的本包终端输入，输出目录换未用过的编号：

```bash
python3 -B "$TRACK_WS/tools/benchmark_submission_realtime.py" --output-dir "$TRACK_WS/writer_baseline_01" --seconds 180 --hz 10
```

应运行约 180 秒，再打印计数与平均/最大延迟，保存 CSV、result.json 和逐拍时间。Ctrl+C 可以中止，但不算通过。无需为了整理文档再重复已经完成的本机测试。

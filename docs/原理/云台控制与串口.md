# 云台为什么会朝目标转：从画面到电机

现在使用的程序做的是：**看目标偏离光轴多少，算出两轴应该转多快，把这两个速度交给开发板。**不需要先得到目标在地图里的位置。

已经确认 `/dev/ttyUSB0` 能持续收到云台 IMU，话题为 `/red_standard_robot1/gimbal`，轴参数 `[1,1,1]`。水平转动主要反映在 `gz`，俯仰主要反映在 `gy`。这些不是待重新打通的链路。尚未完成的是：在 NUC 上运行当前跟踪入口，确认目标偏移后电机方向正确、偏差减小并调好参数。

运行步骤看[云台跟踪](../教程/云台跟踪.md)，逐项操作与调参看[上机调参检查清单](../教程/上机调参检查清单.md)。本文只解释它为什么这样工作，以及哪些结论还不能从上位机代码得出。

## 1 当前实际要运行的是哪条链

```text
/image_raw
  → ArUco 检测：找出指定 ID 和四个角点
  → /team47_tracking/marker_corners
  → visual_servo_node：像素偏差 → 角度偏差 → P/PI/PD/PID
  → /team47_tracking/cmd_vel：Twist 的 angular.z、angular.y
  → C++ robo_bridge：转换成 0x30 串口帧
  → /dev/ttyUSB0
  → 开发板现用固件
  → 两轴电机
```

这条链不经过地图、底盘定位、旧世界坐标控制器或 `hardware_adapter_node`。启动配置依据是 [visual_tracking.launch.py](../../src/gimbal_tracker_bringup/launch/visual_tracking.launch.py) 的 `_setup()`；只有 `with_bridge=true` 才启动串口桥，运动仍默认关闭。

同一入口也运行 PnP，输出 `/team47_tracking/marker_cam`，供观察目标的米制位置。**PnP 不在当前转动闭环的必经路径中**：仅为了让码回到画面中心，不需要先解三维距离。以后比赛定位再使用 PnP、真实外参和底盘位置。

## 2 怎样把画面上的“偏右”变成“往右转”

检测器只跟指定 ID。它把码的四个角点交给控制器，控制器取四点的平均位置作为目标中心。

内参主点 `(cx,cy)` 对应光轴在画面上的落点，不一定等于图像宽、高的一半。程序使用本次有效内参，并先用 OpenCV 去掉畸变，再得到归一化坐标 `(xn,yn)`。忽略畸变时，可近似理解为：

```text
xn ≈ (目标中心u − cx) / fx
yn ≈ (目标中心v − cy) / fy
```

这里图像向右、向下分别为正。程序计算两轴角度偏差：

```text
yaw偏差   = −atan2(xn, 1)
pitch偏差 =  atan2(yn, sqrt(1 + xn²))
```

| 目标在画面中 | 角度偏差的符号 | 相机应怎样转 |
|---|---|---|
| 右边 | yaw 为负 | 向右 |
| 左边 | yaw 为正 | 向左 |
| 下边 | pitch 为正 | 低头 |
| 上边 | pitch 为负 | 抬头 |

源码是 [visual_servo_node.py](../../src/gimbal_control/gimbal_control/visual_servo_node.py) 的 `image_error()`。这个符号表描述程序与协议的约定；实际命令到电机的方向仍按单轴上机试验确认。若一轴越转越偏，先停，再改该轴的 `yaw_sign` 或 `pitch_sign`，不能用更大的 P 补方向错误。**命令符号与 IMU 的轴映射是两回事，不为此改已确认的 `[1,1,1]`。**

例如目标在光轴右边约 90 像素，`fx≈1781`，角度偏差约为 `−0.0505 rad`，即 `−2.9°`。仅看 P 项且 `Kp=2` 时，原始速度约 `−0.101 rad/s`。实际还要经过滤波、死区和限幅，不一定立即输出这个数。

相机投影、内参和 PnP 的学习资料对应[官方第二课](https://blog.secaumene.com/teach/class-2.html)。当前不需要重新做已经完成的相机标定。

## 3 P、I、D 分别在做什么

两轴分别计算，同一轴的输入是角度偏差 `e`，输出是请求角速度 `ω`：

```text
ω = Kp·e + Ki·累计误差 + Kd·误差变化率
```

- **P：偏得越远，转得越快。**默认 `Kp=2`，I、D 均为 0。假设速度执行理想、目标静止，云台按 `ω=Kp·e` 转动时，误差满足 `de/dt=−Kp·e`，会逐渐减小。因此位置跟踪可以先从 P 开始，不必为了凑齐三项立即启用 PID。
- **D：根据偏差正在怎样变化，增减当前速度。**相机正在接近目标时，偏差通常减小，D 项会抑制过快接近；它也会放大检测噪声，所以代码对微分做低通，重置后的第一帧微分为 0。D 不保证任何实机参数都稳定，需要依据实际摆动调整。
- **I：让长时间未消除的偏差逐渐产生额外速度。**例如稳定跟踪仍持续偏一侧，再考虑启用。代码限制 I 对输出的贡献，并在速度已饱和、积分还想继续推向饱和方向时停止累加，避免越积越多。

当前图像 PID 的 D 来自**图像角度偏差的差分**，不是直接拿 IMU 的 `gz/gy` 当 D。IMU 在这个入口主要用于判断反馈是否新鲜、桥是否复位，以及本次姿态变化是否超过试转范围。

源码：[visual_pid.py](../../src/gimbal_control/gimbal_control/visual_pid.py) 的 `AxisPID.update()`。`integral_limit` 限制的是 I 项本身产生的速度，单位 `rad/s`；不是把累计误差直接限制为这个值。

## 4 为什么不会把每个像素的抖动都变成电机抖动

输入端先做一阶低通：

```text
alpha = 新图像间隔 / (filter_tau + 新图像间隔)
滤波后误差 = 上次滤波值 + alpha·(本次误差 − 上次滤波值)
```

随后使用连续死区：死区内按 0 计算，死区外扣除死区宽度，避免刚越过边界就突然跳出一截速度。最后经过角速度上限 `max_omega` 和变化速度上限 `slew`，防止指令过大或突变。

短时丢码也不无期限沿旧方向转：仅在允许的丢失帧数和时间内，将上次指令逐渐衰减；超过条件停止。控制器不会在没有新观测时继续累计 I。持续未见目标、IMU 中断、达到试转时间或姿态变化上限，都会进入停止路径。

这些逻辑在 [visual_servo_node.py](../../src/gimbal_control/gimbal_control/visual_servo_node.py) 的 `on_corners()/tick()/stop()` 和 [visual_pid.py](../../src/gimbal_control/gimbal_control/visual_pid.py) 的 `ErrorConditioner`。检测图像到来时更新 PID；控制定时器按配置频率发送最新指令，两者频率不必相同。

默认与可调范围以 [visual_tracking.yaml](../../src/gimbal_tracker_bringup/config/visual_tracking.yaml) 和源码校验为准。当前图像控制的增益、滤波、死区、控制频率和限幅会在运行时重新读取；**这不表示目标位置卡尔曼滤波器的噪声参数也支持动态修改**，后者是在启动时构造的。

## 5 ROS 消息怎样变成串口字节

控制器发的是 `geometry_msgs/msg/Twist`。在这条专用云台话题中，只使用：

```text
angular.z = yaw_omega，单位 rad/s
angular.y = pitch_omega，单位 rad/s
```

虽然名字是 `cmd_vel`，这里并不让底盘运动。桥按启动参数订阅 `/team47_tracking/cmd_vel`，读取两个数并编码：

```text
帧头 AA | 目的地址 EE | 功能号 30 | 数据长度 08
| yaw速度 float32小端 | pitch速度 float32小端 | 两个校验字节
```

整帧 14 字节。它不含目标 ID、像素坐标、目标角度或 PID 增益。**下位机通过这条指令知道“按这两个速度转”，并不知道画面里选中了哪一个码。**

对应 [bridge_node.cpp](../../src/42-gimbal_serial/src/bridge_node.cpp) 的 `BridgeNode::onCmdVel()`、[protocol.hpp](../../src/42-gimbal_serial/include/gimbal_serial/protocol.hpp) 的 `encodeCmd()`。C++ 桥在这里负责检查数值、编码和发送，不在这里实现电机的速度环。

开发板通过 0x01 回传 IMU，桥把它发布成 `/red_standard_robot1/gimbal`。收到连续 IMU 已证明通信和这段反馈链工作，但它没有回传完整 CAN 状态、编码器或电机使能状态，不能仅凭 IMU 宣布电机已经正确跟踪。

停止时，上位机请求几帧零速度后停止发送。协议中的“无新指令约 0.5 秒开始减速、约 3.5 秒松弛”是固件约定，尚未测过当前设备的实际制动时间。持续发送零速度仍会刷新看门狗，不等于断电。详情见仓库 [协议](../../protocol/PROTOCOL.md) §4、§10 和[官方在线协议](https://blog.secaumene.com/kit/protocol.html)。

## 6 旧的 PD 加前馈代码为什么还在

仓库另有面向场地坐标目标的控制分支：

```text
PnP → 完整坐标变换 → 目标位置和速度
  → gimbal_controller_node / ControlLaw
  → /gimbal/cmd_omega
  → hardware_adapter_node
  → /offboardlink/cmd_vel_gimbal
  → C++桥 → 同一种 0x30 帧
```

它与当前图像伺服是两个入口，**不要同时往同一真实串口发送**。当前 `visual_tracking.launch.py` 不启动这套旧控制器和适配器。

旧控制器先计算目标相对云台的视线 `r=目标位置−云台位置`，由 `atan2` 得到目标方向，再与当前朝向比较。它还用目标相对相机的速度计算“视线本身正在转多快”，作为运动前馈。简化表达为：

```text
角速度指令 = 前馈增益·视线角速度
           + Kp·角度误差
           − Kd·(实测角速度 − 视线角速度)
           − 底盘转动贡献
```

前馈使目标移动时，云台不必等偏差积累起来才开始追。这里的 D 是速度误差反馈，与上文当前图像 PID 的误差差分不同。底盘转动补偿需要与下位机的速度定义一致，不能因为台架静止时能跟踪就认为装车后语义已经全部确认。

源码：[control_law.py](../../src/gimbal_control/gimbal_control/control_law.py) 的 `target_angles()/feedforward()/ControlLaw.compute()`、[gimbal_controller_node.py](../../src/gimbal_control/gimbal_control/gimbal_controller_node.py)、[hardware_adapter_node.py](../../src/gimbal_serial_bridge/gimbal_serial_bridge/hardware_adapter_node.py)。这一分支依赖有效世界对齐、安装模型、底盘状态和关节状态，当前桌面入口不等待这些条件。

## 7 C 板收到速度以后，究竟如何驱动 DM 电机

上位机源码只能确认“发送两轴速度设定值”。它不能证明当前烧录固件怎样执行速度环。

一般速度环会比较 `请求速度−实测速度`，根据差值调整电机力矩或电流，让实际速度靠近请求速度。但这只是原理说明。现场固件可能自己做 PI/PID，也可能使用电机驱动器的速度模式，或采用 MIT 模式中的速度、阻尼和力矩项。**没有现用下位机工程或可靠版本资料，不能选定其中一种当成事实。**

要确认最后一段，需要现用固件的串口 0x30 接收函数、速度控制函数、CAN 电机发送函数及参数，并核对使用的电机模式、速度反馈和指令单位。还要确认请求速度是相对底盘关节轴的转速，还是惯性稳定转速；这是装车补偿需要对齐的接口。无须为此擅自刷写任何固件，也不以此推迟当前上机跟踪试验。

| 已经掌握 | 尚未证明 |
|---|---|
| 当前图像误差、P/I/D、滤波和串口编码算法可从源码确认 | 当前增益在真实设备上的收敛速度和振荡情况 |
| `/dev/ttyUSB0` 与连续 IMU 已有现场记录 | 当前入口的两轴指令是否按预期执行，须实际跟踪验收 |
| 虚拟云台能够解释和验证上位机控制逻辑 | 虚拟动力学不能代替实际 DM 电机、负载和固件内环 |
| 协议规定了 0x30/0x01 的格式与方向 | 现用固件的 PI/PID、DM 模式、CAN ID 和真实停机时间 |

你们下一步要观察的核心事实很直接：**码偏向哪边，相机就朝哪边转，偏差应减小；静止目标不应持续左右摆动。**其余原理用于解释和排查这个现象，不能替代它。
